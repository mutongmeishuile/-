# 常见坑 · 地图 SVG 与图例

> 从 `SKILL.md`「常见坑」拆出。触发词：图例放进地图 / 图例只有文字没图形 /
> 地图图例手机版不可读 / 剖面标签互压 / 虚线用错 / 步道配色。
> 配套：`references/legend-and-color.md`（色相分配与图例样本细则）。

## 1. 图例要放进地图的空白区

**别单摆在页面下方**：读者「看图 → 翻到下方查图例 → 回图」来回对照，
是最常见的可读性抱怨（用户原话「图例单独在下方，需要对比查找」）。做法：

1. **先量轨迹分布找空白矩形**（栅格化点位计数即可，别靠肉眼看）。
   判据是**该矩形内轨迹点 = 0** 或极少。
   例：南天山北线 `x>980 且 y<790` 区域 0 点为空白（轨迹最上点 y=796），
   尺寸 524×790 unit，正好放一个两列小图例。
2. 用**半透明白底 + 细边**（`fill-opacity≈0.97`）压在空白处。
   ⚠ 不透明度给到 **0.95 以上**（用户明确要求"90% 以上"）：半透明虽能看到底下地形，
   但图例文字与底图等高线数字叠在一起会互相干扰。
3. **面板必须先登记进标注占位区**（`_OCC`），否则后画的标注会压上去 ——
   登记时机要在摆 POI 文字**之前**。
4. 面板几何与图例内容分离：`_IL_X/_IL_Y/_IL_W/_IL_LH` 常量给占位用，
   `_inset_legend()` 出内容；`panel_h` 要**动态算**（`y + 8 - _IL_Y`），
   否则加一行图例就会溢出面板。
5. **地图内图例必须给个 class（如 `g.il`），手机版用 CSS 隐藏它**：见 §3。

## 2. ⚠ 地图内图例的两个隐蔽 bug（症状＝只有文字、图形不见了）

两个都真实返工过。

### bug 1：样本坐标不能用外层 `<g translate>` 叠加

样本工厂（`_il_line` / `_il_pin` / …）内部一旦已经算成**绝对坐标**
（含 `_IL_X` 与 `y`），外层再套 `translate(_IL_X+4, y-…)` 就是**二次平移** ——
样本被推到 x≈1996（画布 1504）之外，整列图标看不见，只剩文字。

**正解**：统一「样本工厂出绝对坐标，行渲染函数不再平移」，并在 docstring 写死这条约定。
**用脚本把生成的 SVG 里所有 `<rect>`/`<line>` 的 x 值打出来核对**是否落在面板内 ——
这类"坐标算飞了"的 bug 肉眼看渲染图很难定位。

### bug 2：样本必须在循环里「即时」构造，不能写进列表字面量

```python
for sw, nm, ds in [(_il_line(..., y), "计曲线", ...), (_il_line(..., y), "首曲线", ...)]:
```

列表在构造时 `y` **只求值一次**，6 个样本全被钉在同一个 y 上（实测六条线全挤在 y=572）。
改成：

```python
[(lambda yy: _il_line(..., yy), "计曲线", ...), …]   # + mk(y) 即时求值
```

### 附：两个视觉必需项

- **样本底版（`#F6F2EB`）是必需品，不是装饰**：细线样本（首曲线、步道、溪流）
  画在纯白面板上对比度太低会"消失"；而带白描边的样本（实测轨迹）在纯白上又会丢掉描边。
  统一给每行样本垫一块浅暖纸色底板。
- **所有样本要共用同一块底板**：线/面有底板、点没有，样本列会读成"两种东西"。

## 3. ⚠ 地图内图例在手机版必然不可读 → 必须做「双份」

地图 viewBox 固定，手机版心 430 → 370 CSS 时缩放比只剩 **0.25**，
图例 15.5 unit 的字落到屏幕上约 **3.8 px**，完全读不了
（桌面版 0.485，尚有 7.5 px 可读）。正解：

- 桌面版 → 显示地图内图例（`g.il`），**隐藏**页面下方那块 `.rbox-lgm`；
- 手机版 → `g.il{display:none}` + `.rbox-lgm{display:block}`，在页面下方出文字版图例
  （手机单栏阅读本就顺手）。
- 一份 SVG + 一份 HTML 图例，靠 CSS 断点切换，**不用出两份地图**。
- 注意这是与「剖面图」相反的取舍：剖面是**两份 SVG**（`.prof-d`/`.prof-p`）因为要留在原位读；
  而地图图例**可以换位置**，所以用「隐藏/显示」比复制整张地图省得多。

⚠ **但这只适用于"可以换位置"的元素。地图上的地名不行 —— 它们必须留在原位。**
所以结论要分两半：

| 元素 | 手机版怎么办 | 理由 |
|---|---|---|
| 图内图例 | CSS 隐藏 + 页面下方文字版图例 | 可以换位置 |
| 地名 / 点位符号 | **另出一份手机版地图 SVG** | 必须留在点位旁 |

手机版的放大倍率要**算不要猜**：`缩放比 = 版心内地图宽 / viewBox 宽`
（本例 370 / 1504 = 0.246），目标 10 CSS px → 字号需 `10 / 0.246 ≈ 42 unit`
= 桌面 22 unit 的 **1.9 倍**。配套三件事：

- **文案要缩短**（去掉海拔后缀，`夏羌拉垭口 · 全程最高` → `夏羌拉垭口`）：
  长标签在放大后根本放不下，海拔在关键点表里查得到，不必在图上重复；
- **`dx/dy` 同比放大**，否则改完字号标注会"悬空在远处"；
- 手机版**不占图例的位**（`_OCC` 里不登记），白省一大块可用区域；
  底图 JPEG 也可以按 ~820 px 嵌（手机上只显示 ~740 device px，嵌 1504 纯属浪费体积）。

## 4. 图例样本必须由出图参数生成

**不能另画一套色块**：`<i style="background:#7B5A3E">底图细线＝步道</i>` 这种写法等于没画 ——
一旦改了出图配色，图例就指向旧色。做法：图例样本与底图**共用同一组常量**
（色值、线宽、膨胀量都从同一处取），或直接复用生成样本的工厂函数。

配套见 `references/pitfalls-terrain.md` §7「改色 = 多处同源一起改」。

## 5. 剖面标签：先缩字宽，再调 dy（顺序别反）

山峰/垭口/营地在剖面上扎堆时，**第一反应不该是加 `dy` 错落** —— 那是最后手段。
正确顺序：

1. **先量标签宽度**：`宽 ≈ len(文案) × 字号 × 0.94`（汉字按 1 字宽、带白描边 halo 再留余量）。
   例：`"阿苏萨拉达坂 3874 m"` @12 px ≈ **113 px**，两条就必然要错开 ≥113 px 才不压；
   而 `"阿苏萨拉达坂"` @10.5 px ≈ **55 px**，同样两点差 60 px 就能并排。
2. **去掉文案里的海拔后缀**（`"第三天营地 3641"` → `"第三天营地"`）：海拔在
   `BOT_LBL`、关键点表、地名卡里都能查到，剖面标注不需要重复 ——
   这一步常直接把宽度砍半，比任何 dy 都有效。
3. **把 MARKS 字号从 12 降到 10.5**（高亮点 12.5→11，字重 800→700）。
   10.5 px 配白描边在小屏仍可读。
4. 做完 1–3 后仍冲突的，**才**用 `dy` 错落，量级只需 ±24 px（原方案要 ±50～82 才勉强拉开）。

- ⚠ **不要一上来就写穷举脚本解 dy 阶梯**
  （`itertools.product(range(-30,60,6), repeat=N)`）：在 6 个变量上会跑到超时被杀（SIGTERM），
  而且**根因是字宽不是 dy**，穷举出来的解也是"字挤字但程序说没重叠"。
- **同一 y 层最多放 2 个标签**（左一个右一个）；第 3 个必须换层。

## 6. 虚实线的使用纪律

**实线/虚线只在确有数据分级时才用**。有真实轨迹就全线实线，
别为了"看起来专业"硬把某些段画成虚线 —— 那会让人误以为那段是猜的。
只有 OSM 测绘段 + 拟合段混排时才用虚线区分，且必须图例注明。
（轨迹来源优先级见 `SKILL.md` §轨迹来源。）

## 7. 步道配色必须换「色相」

底图已经把棕给了等高线（首/计曲线）、蓝给了水系、绿给了林地，
橙黄原属公路（现公路改白芯暖边后腾空，但仍与实测轨迹的橙红太近）。
所以步道要**换色相**（如紫 `#743482`），不是换明度 —— 换明度在同一色相里仍然撞。
色相分配全表见 `references/legend-and-color.md` §1。

补充（党岭一役的三条修正）：

- **步道最终用"中性灰"最稳**：换成紫之后又撞上攻略主线 D3 的紫；换橙又撞 D1 的橙红。
  底图元素**不该带色相**，中性灰 `(140,138,134)` 与任何主线色都不会撞，
  靠明度 + 虚线节拍 + 线宽三层区分即可。
- **⚠ 步道的浅色描边（casing）在"芯变暗"之后会反客为主**：芯色从紫改成灰之后，
  原来那圈纸白 casing 成了全图最亮的东西，视觉上读成一片白"鬼线"。
  → 芯色改暗后**必须同步去掉 casing**（`C_TRAIL_CASING = None`），
  或把 casing 改成比芯更暗的颜色。判据：casing 不能比周围底图亮。
- **公路也要给轨迹让路**：原橙色公路与 D1 橙红主线太近，改为**暖砂色**
  （芯 `(240,208,172)` / 边 `(200,170,144)`）后不再抢戏。

## 8. ⚠ 标注避让：不要「先定方案、再从上到下试」

自动避让写成

```python
for hdx, hanc in hplans:        # 外层是"方案"（左放 / 右放 / 居中）
    for ody in cand:            # 内层是纵向候选
        if fits: return         # ← 主方案只要在 ±5 行内找到位置就立刻返回
```

会有个隐蔽后果：**主方案在第 5 行能放、备选方案在第 0 行就能放时，它选第 5 行。**
本例手机版把字号放大 1.9 倍后，「夏羌拉垭口」就这样被甩到离点位 **285 unit**（约 70 CSS px），
加了引线也读不出来是哪座山。

两条修正一起做才有效（只做第一条没用，因为主方案总能"成功"）：

1. **把（方案 × 纵向）全部候选摊平，按"离自己点位最近"择优** ——
   `cost = hypot(水平间隙, 纵向间隙)`，取最小值；
2. **摆位顺序按"越挤越先摆"，不是按里程序**：先到先得，密集区的点如果排在后头，
   等轮到它时近处已被占满。`key = 到最近其他点位的距离`，升序。
   本例：手机版最远距离 285 → 78 unit（中位 52），桌面版最大 71 → 71、其余全部 ≤30。
3. `anc="middle"` 的锚点原先**只能上下动**，补两个横向兜底
   （`(±(w/2+34), start/end)`），否则上下全被占住时无处可去。

## ⚠ 手机版密集区：整列被"图标+邻居标签"上下夹死，标注掉进兜底 clamp 造成重叠

珠峰东坡线手机版（1504×956 画布、字号 1.7×）自检一直报 1 对重叠，根因不是字号太大：
**某个点位的整条横向列被上下夹死**——上方是邻居的标签、下方是再下一位邻居的图标占位
（图标占位 `_OCC` 是按 `±_PIN_R` 整块登记的，比标签更"宽"）。
该点所有纵向候选（±7 行）逐个被拒，最后走兜底 clamp（不查冲突）压到别人头上。

**修法：给 `_layout` 的横向候选加"更远的同侧 / 更远的对侧"两档**（如 `±(clear+64)`），
让被夹死的点能整体平移出夹缝；代价函数（离自己点位的距离）自会优先近档，
远档只在被夹死时才用，不影响其他标注。光调 dy/字号没用——列是死的，行怎么挪都在列里。

配套：给自检的"重叠"输出**打印两个冲突框的坐标和各自点位坐标**（`#名 pt=(x,y) box=(x0,y0,x1,y1)`），
一眼就能看出"谁被夹在哪两块之间"，不用逆向推理占位顺序。

## 9. ⚠ 地图「三件套」：缩小 + 动态落点，硬约束是**不压轨迹**

三件套 = **图例**（`g.il`）、**指北针**（`compass`）、**比例尺**（`scalebar`）。
它们是最容易被当成"背景装饰"随手钉在四角的东西，而轨迹是会变的 —— 于是常见症状：

- 图例正好压在连续爬升段上，把那截轨迹盖掉；
- 指北针压住第一个 POI 的符号与其标签；
- 比例尺横跨山脊，读图时被误当成一条等高线；
- 三件套本身太大，喧宾夺主（在 1504 宽的画布上，原图例 566×218 占了近 6% 面积）。

**规矩：**

1. **尺寸先缩小**。`map_svg.py` 的三个系数，按"面积 ≈ 系数²"理解：
   ```python
   FURN_LG = 0.78   # 图例 566×218 → 442×170，面积 ≈ 0.61
   FURN_CP = 0.72   # 指北针直径 42 → 30
   FURN_SB = 0.80   # 比例尺
   ```
   缩小后文字必须仍可读 —— 少一行图例项，比缩小到 9 px 更好。

2. **落点交给求解器，不要写死四角**。`guide_common.Placer`：

   ```python
   P = GC.Placer(IW, IH, track=overlay_track_pts, pad=22, track_half_w=5.0)
   P.labels = 已经定好的标注框      # 软避让：重罚（weight_label=1000）
   P.pins   = 已放置的 POI 圆心     # 软避让：重罚（weight_pin=400）

   lg = P.place(w_lg, h_lg, prefer=("tr", "tl", "br", "bl", "mr", "ml"))
   cp = P.place(w_cp, h_cp, prefer=("tr", "tl", "br", "bl"))
   sb = P.place(w_sb, h_sb, prefer=("bc", "br", "bl"))
   ```

   - **硬约束**（命中即否决）：不与已放置的家具矩形重叠；**不与轨迹相交**（`allow_track=False`）；
     不出画布。偏好序 + `ins ∈ (0,14,28)` 三级内缩，贴边不成就往里退。
   - **软约束**（进代价函数）：压标注框 ×1000、压 POI 符号 ×400、压轨迹点数 ×3、偏好序 ×6/名次、
     内缩 ×0.05。取总代价最小者。
   - `prefer` 要给足候选（至少 4 个锚点），否则窄画布上可能无解返回 `None`。

3. **摆放顺序：家具先、标注后**。家具是硬约束（挡轨迹就是错），标注是软约束（挪一格就行）。
   反过来先摆标注，家具会去"绕"标注，容易把家具挤到轨迹上 —— 顺序错了就白做。
   摆完标注后，若要让标注也绕开家具，把家具矩形塞进 `Placer.taken` 传给标注布局即可。

4. **轨迹相交用栅格预筛，别逐点算**。`Placer` 把轨迹（含线宽膨胀）栅格化成 `CELL=24` 的
   `set[(cx,cy)]`，判断矩形是否压轨迹时只查它覆盖的格子 —— O(1)。膨胀格数
   `grow = int(half_w // CELL) + 1`：**忘了 +1 就会漏判刚好擦边的线段**，症状是"偶尔有一件家具
   轻轻压住轨迹"（概率性出现，比稳定压住更难查）。

5. **必须自检、并把结果并进失败码**。`map_svg.self_check(mobile, placed)` 打印五项：

   | 检查 | 期望 |
   |---|---|
   | 标注越界 | 0 |
   | 标注两两重叠 | 0 |
   | **标注压轨迹点** | **0** |
   | **家具互相重叠** | **0** |
   | 标注压家具 | 0 |

   后两项是三件套引入的新约束，缺了就等于没做。**自检里 0 值是唯一能替代"用眼睛看"的东西** ——
   尤其是轨迹很密时，肉眼根本看不出图例压没压住。

6. 高清地图（`render_map_hi.py`）复用同一份 overlay，所以三件套的位置在三张图上**完全一致**
   （长图 / 高清图 / HTML 内嵌 SVG 共用 `build_svg`）—— 别在某一处单独挪位置。

## 10. ⚠ 多日线路（>2 天）：分日配色必须按 `day_bounds` 画 N 段（2026-10-09 亚丁大转山）

`build_map_overlay` 早期只认 `route["split1"]`，于是循环体写成

```python
for seg, col in ((XY[:SPLIT_I + 1], D1_C), (XY[SPLIT_I:], D2_C)):   # ❌ 只有两段
```

**5 天线路跑出来 D3/D4/D5 全被画成 D2 的绿色**，图例里却有 5 条彩色线段 —— 图例与图不一致，
而且**自检全绿**（标注、越界、家具都正常），只能看图发现。

正解：颜色与分界都从 CFG 读，段数由 `day_bounds` 决定：

```python
_day_cols  = [d.get("color", D1_C) for d in _CFG.get("days", [])] or [D1_C, D2_C]
_bounds_km = [0.0] + [float(b) for b in _CFG.get("day_bounds", [])] + [float(TOTAL_KM)]
while len(_day_cols) < len(_bounds_km) - 1:      # 段数多于颜色 → 沿用末色
    _day_cols.append(_day_cols[-1])
# 按 km 找索引，逐段生成 <path>
```

配套：**分日界虚线也要每条都画**（原来只画 split1 那一条）；
没有 `day_bounds` 时退回"单分界两天"的老行为，保证老线路不受影响。

## 11. ⚠ 图例要「列全符号 + 别占地」：两列网格 + 只列用到的 kind（2026-10-09 亚丁）

用户原话：「图中所涉及的图例最好在图例区域都展示出来，不要占地过大，动态调整」。
原来的图例只有**分日线段 + 一条步道虚线**，图上那些「起/终/营地/水源/垭口/主峰」符号
在图例里**一个都没有** —— 读者看到图上有个橙三角，翻图例找不到对应说明。

做法（已实现于 `map_svg._legend_symbols()`）：

- 遍历 `GC.pois_of(RD)`，**只收集图上真的出现的 kind**（换线路自动适配，不需要手维护清单）；
- 顺序固定为 `start/end/camp/water/warn/peak_hi/peak/temple`，**两列网格**排布
  （n 个符号只占 ⌈n/2⌉ 行，比单列省一半高度）；
- 每个样本用 `mk_pin(0,0,kind)` 外面套 `<g transform="scale(0.42)">` 生成 ——
  **图例样本与图上符号由同一个函数产出**（见 §4），改符号定义不会漏改图例；
- 名称默认在 `_KIND_NAME`，可用 `CFG["legend_kind_names"]` 覆盖
  （本线把 `warn` 改叫「垭口」——这类"本线语义"只有 route_def 知道）；
- `_legend_size()` 的高度公式要**跟着加上符号区的行数**，否则符号会溢出卡片。
- 尺寸系数 `FURN_LG` 收到 **0.66**（用户要求"再小一点儿"），行高 44、字号 16.5–21 一并等比缩。

## 12. ⚠ 比例尺：色条长度不能被 FURN_* 缩放，底衬必须比色条宽（2026-10-09 亚丁）

第一版改动只把比例尺"细身化"了，用户第二轮仍指出**「比例尺下面的底纹与比例尺不协调」**。
回看渲染图才发现两个硬伤：

1. **底衬框比色条还窄 → 色条直接戳出框外，压在底图花纹上。**
   原因：`SB_W = (sb_bar + 46*M) * FURN_SB` —— 把**色条长度本身**也乘了 0.68。
   色条是量距离用的，**长度绝不能被装饰性系数缩放**（缩放后"1 km"就不等于 1 km 了）。
   正解：
   ```python
   sb_bar = 1000 / M_PER_PX                 # 真实长度，不乘任何系数
   SB_W   = round(sb_bar + 2 * sb_pad)      # 底衬 = 色条 + 两侧内衬
   SB_H   = round(30 * M * FURN_SB)         # 只缩"高度/字/内衬"
   ```
   色条用 `bx = sx0 + (bw - sb_bar) / 2` 在框内**居中**。
2. **框内留白过大**：数字与色条之间空一大截，视觉上"底衬一大块、内容一小条"。
   → 数字基线固定为 `bar_top - 4.5*M`（紧贴色条），色条底边距框底 `9*M*FURN_SB`。
3. 配色也顺手统一：底衬 `fill="#FBFAF7" opacity 0.94` + `stroke="#CFC7B9"`，
   与页面卡片同色系（此前是纯白 0.86，地形透过来显得"脏"）。
4. **长度取 2 km 而不是 1 km**：本图（逻辑宽 1504 px 覆盖约 18.8 km）1 km ≈ 80 逻辑 px，
   取 1 km 时"0.5"与"1 km"两个数字**正好贴在一起**（实测撞字）→ 取 2 km，档位 0 / 1 / 2 km。
5. ⚠ **卡高必须按字高算，不能只按 `FURN_SB` 缩**：数字字号不参与缩放（它是信息），
   若卡高跟着 0.62 缩到 18.6 px，数字基线只剩 4 px 余量 → **数字溢出卡片上沿被切掉**
   （实测："0 1 2 km"三个数字上半截没了）。正解是把卡高写成显式几何：

   ```python
   SB_H = round(sb_top + sb_fs + sb_gap + sb_th + 6 * M)   # 上衬 + 字高 + 间距 + 条高 + 下衬
   num_y = sy0 + sb_top + sb_fs * 0.95                     # 基线位置由字高推出来
   ```

   同理**信息性文字（比例尺数字、公里数）一律不参与 `FURN_*` 缩放** —— 缩放只作用于装饰
   （内衬、圆角、字重视觉级别）。qa 会打印"最小字号"，被压到 < 11 px 说明缩过头了。

配套：**改比例尺尺寸后要重跑 `shoot_guide` / `render_map_hi`**（三件套位置由 `Placer`
动态求解，尺寸一变落点会跟着变），并确认 `self_check` 的「家具互相重叠」仍为 0。

## 13. ⚠ 文字描边别超过字号的 ~15%：厚白边会糊成「白色阴影」（2026-10-09 亚丁）

用户原话：「字体看上去有白色的阴影，可以去掉或者改成其他美观的样式？」
点位的白描边当时是 `stroke-width = 5.4 * PS`，PS=0.85 → **4.6 逻辑 px ≈ 9 栅格 px**，
而字号只有 17.9 逻辑 px —— 描边占字号 26%，在浅色地形上就糊成一圈白晕（本该是"描边"）。

- **经验值：描边宽度 ≈ 字号的 11–15%**（17.9 px 字号 → 2.4 px 描边），
  再加 `stroke-opacity 0.92` + `stroke-linejoin="round"`，读起来是干净的轮廓线；
- 底图侧同理：等高线数字 `2.0*S → 1.7*S`、峰名/湖名 `2.8*S → 2.1*S`；
- 引线（leader line）的白底也要跟着收细（`4*M → 2.6*M`），否则引线比字还抢眼；
- **不要为了"去掉阴影"把描边全删** —— 浅底图能读，深色晕渲/林地那一片就没了。
  "细而净"才是正解，纯删描边是另一种翻车。

## 14. ⚠ 图例的三处"对齐/尺寸"细节（2026-10-09 亚丁，用户连提两轮）

1. **样本线要压在文字的视觉中线上**。文字是"基线定位"（`y = 行基线`），线是"中点定位"，
   两者直接给同一个 y 就会错位。公式：字形中线 ≈ 基线 − 0.35 × 字号。
   实测：字号 19×S、基线 `ry+11*S` → 线应画在 **`ry+4.4*S`**；
   原来写 `ry-7*S`，比文字中心高 11×S（≈6 逻辑 px），用户直接圈出来说"错位"。
   同样的坑适用于：图例样本、指北针的 N、任何"图标 + 文字"同行排版。
2. **样本线宽不要超过字号**。原来 6.5 px 的横杠配 9.35 px 的字，线比字还抢眼；
   收到 **3.8**（虚线步道 1.5）后就清爽了。
3. **卡片高度必须由内容推出，且尺寸函数与渲染共用同一组常量**。
   曾出现"脚注压住最后一行符号"——`_legend_size()` 里写死 `96 + 52*rows`、
   而渲染用的是 `60 + 44*i`，两套数字各走一套，卡片偏矮，脚注就叠到末行上，
   **自检（越界/重叠/压轨迹）全绿，只能看图发现**。
   正解：抽 `_legend_geom()` 统一产出 `{last_row, end, h, foot, tail}`，
   渲染全部引用 `LG_*` 常量；并加一条开发期护栏：

   ```python
   if g["tail"] < LG_MIN_TAIL:      # 脚注与末行内容的最小安全间距
       print("⚠ 图例几何异常：脚注与末行间距仅 … —— 调大 LG_BOT")
   ```

   经验值：符号行末行中心 → 卡片底至少留 **46×S**（脚注基线 = 卡高 − 14×S）。
