# 用真实 XYZ 瓦片做地图底图（并叠加真实轨迹）

当用户指定了一个瓦片服务（如 `https://hiking.318318.xyz/t05/{z}/{x}/{y}`）时，用它替换手绘示意底图。
**这套做法的关键是：底图是真实经纬度投影，所以线路与标注必须换成真实经纬度，否则对不上。**

> **阅读提示**：§7、§11–§14 是**贡嘎项目的实战复盘**（案例叙事）。文中出现的
> `make_base_tile.py` / `replay_tint.py` / `probe_dem.py` / `fetch_tiles_cyc` 是**当时的临时脚本**；
> 现在对应的能力已经收录成正式脚本，按下面的对应关系读：
>
> | 复盘里的临时脚本 | 现在的正式脚本 |
> |---|---|
> | `fetch_tiles_cyc` + 拼贴 | `build_base_map.py`（瓦片下载 + 拼接 + 投影） |
> | `make_base_tile.apply_terrain_tint` / `draw_dem_contours` | **`tile_tint.py`**（线画掩码 + 抹除自带等高线 + DEM 设色/等高线） |
> | `replay_tint.py`（只重放上色，不重拼瓦片） | `tile_tint.py --tile out/base_tile.jpg`（同样是"拼一次、多次上色"） |
> | `probe_dem.py` | `make_terrain.py` 内建的窗口/高程打印与 `tile_tint.py --selftest` |
>
> 看这几节要的是**结论与教训**，不是照抄脚本名去运行。

## 0. 瓦片源清单（务必先看合规，再挑好看）

严格说 **OSM 官方只有一种风格（standard），并没有"官方地形图"**。所谓"OSM 地形图"都是社区/厂商拿
OSM 数据 + DEM（SRTM 等）自己渲染的。可用的地形类源（`scripts/tiles.py` 的 `SOURCES` 已内置）：

| 源 key | 内容 | 最高 z | 实测 | 许可/合规 |
|---|---|---|---|---|

| `opentopomap` | **最正统的"OSM 地形图"**：OSM 数据 + SRTM，等高线 + 山名 | 17 | ❌ 2026-09-29 大陆网络 DNS 污染：`a.tile.opentopomap.org` 解析到 **104.244.46.246**（Twitter 段），连接即超时；换 host/DNS 均无效 | CC-BY-SA，允许（含商用），但明确要求**不要 Massendownload**，需署名 |
| `esri_hillshade` | 纯晕渲（灰度），地形最细腻 | 16+ | ⚠️ **分区域**：九华山（华东）z12–z16 全通；**川西贡嘎一带 z13–z16 一律返回 "Map data not yet available" 灰底占位图**（2521 B、std≈3.4，靠 32×32 std 判据识别） | Esri 公开服务，需署名 |
| `esri_topo` | 地形注记图（等高线 + 高程点 + 地名） | **13** | ⚠️ z12/z13 通，**z14+ 返回空白占位图**；且中国西部大量区域无数据 | Esri 公开服务，需署名 |
| `osmde` / `osmfr` | 标准 OSM 风格（非地形），地名/高程点齐全 | 19/20 | ✅ z12–z16 全通 | OSM 贡献者，需署名 |
| `318318` | 原专线地形渲染（等高线 20 m） | 17 | ❌ 2026-09-29 起整站 567 | 上游 openmaps.fr |
| ~~`tile.openstreetmap.org`~~ | 官方标准风格 | 19 | — | **Tile Usage Policy 明确禁止批量下载/爬取，不要用** |

**合规红线（重要）**：生成一份攻略长图 ≈ 1300 张 z15 瓦片，属于"批量"。官方 OSM 瓦片站明文禁止这种抓取；
OpenTopoMap 是捐赠维护、也要求不要过量。因此：

- **一次性、低频、单张成品** → 用 OpenTopoMap / Esri + 署名 + 本地缓存（`tilecache/`，避免重复请求），可接受；
- **要反复出图 / 大面积 / 商用** → **自建底图**：下载开放 DEM（**Copernicus GLO-30** 或 SRTM 1″，均免费开放），
  用 GDAL 出等高线 + 晕渲（`gdaldem hillshade` / `gdal_contour`），再叠 OSM 路网矢量。完全合规、无速率限制、可无限重出。
  这是"原生 OSM 地形图"的正解。

### 占位图自动识别（与源无关）

不同源的失败形态不一样（318318 返回上游 "Access denied"、Esri 返回灰底 "Map data not yet available"、
Carto 返回 "API KEY REQUIRED"）。`tiles.py` 用**与源无关**的判据：解码后把图缩到 32×32，
若灰度标准差 < 2（近似纯色）即判为无效 —— 一次覆盖所有占位图，不靠 HTTP 200 或文件大小猜。

```bash
python scripts/tiles.py                  # 逐个源探活 z12–z16
python scripts/tiles.py opentopomap esri_hillshade
```

Esri 的坑：`World_Topo_Map`、`World_Shaded_Relief`、`World_Terrain_Base` 在中国区域**只到 z13**，
z14 起是空白；`World_Hillshade` 到 z16+。所以"Esri 地形图"不能直接用于 z15 出图。

## 1. 先探通瓦片服务（两个必踩的坑）

### 坑 A：URL 不能带扩展名

用户给的模板通常是 `/{layer}/{z}/{x}/{y}`（如 `/t05/15/27108/13470`）。

- **正确**：`https://hiking.318318.xyz/t05/15/27108/13470` → 200，256×256 真瓦片
- **错误**：加 `.png` → 200 但返回的是上游 `openmaps.fr` 的 **"Access denied" 占位图**（约 10 KB，254×254，黄黑斜纹）

识别方法：合法瓦片 17–55 KB；占位图固定 ~10387 字节、254×254、调色板 `P` 模式。**别只看 HTTP 200。**

### 坑 B：不能带浏览器 User-Agent（EdgeOne WAF）

该站前置腾讯云 EdgeOne。**带 `Mozilla/...` UA 的请求一律返回 HTTP 567 拦截页**（7352 字节 HTML，含"请求已被站点的安全策略拦截"）。不带 UA 反而 200。

- curl：用 `curl -A ""`
- Python：用 `http.client`（默认不发 UA），**不要用 requests/urllib 的默认头**
- 无头 Chrome 也不行——它必带 UA，**因此不能用"浏览器直接截瓦片图层"的方案**，必须自己下载瓦片再拼接

### 探针脚本

```bash
python scripts/tiles.py          # 探测 z13–z17 是否可用
```

输出各 zoom 的字节数与可用性。确认后可用的最高级别（本例到 z17）通常再退一级用，兼顾清晰度与下载量。

### 常见响应码对照

| 现象 | 含义 |
|---|---|
| 200 + 17–55 KB / 256×256 | 正常瓦片 |
| 200 + 10387 B / 254×254 | 上游拒稿占位图（多半是加了 `.png`） |
| 567 + HTML | WAF 拦截（多半是带了浏览器 UA） |
| 401 + 52 B | 该图层需授权（`t03/t04`） |
| 404 + 555 B | 该图层不存在（`t01/t06/t07`） |

### 服务可能整体挂掉（务必先探活）

站点会**整段不可用**：所有 zoom、带不带 UA、带不带扩展名**一律 567**。此时不是你的请求姿势问题，是站点侧拦截策略收紧了。

- 处置：**不要死磕**。若工作区里已有一版生成过的 HTML，它的 `<img src="data:image/jpeg;base64,...">` 里就嵌着上次的完整底图，直接 base64 解码还原 `out/base_map.jpg`，并把 `build_base_map.py` 的窗口 bbox 改回**上次成功那一版的 bbox**（`out/base_meta.json` 里也留着 `box`/`bbox`/`z`/`tx0`/`ty0`），即可继续出图；
- 探活脚本：`python scripts/tiles.py`（逐源探活 z12–z16，并做"解码后缩到 32×32 看均值"的与源无关判据）。

## 2. 取真实坐标：Overpass + OSM

底图是 OSM 渲染，所以**关键点坐标必须也来自 OSM**，这样山峰/寺院/垭口与底图标注天然对齐。

```bash
# peaks / saddles / temples / villages
curl -s -H "User-Agent: hiking-guide-builder/1.0" \
  --data-urlencode 'data@query.txt' https://overpass-api.de/api/interpreter -o poi.json
```

注意 **Overpass 反过来要求带 UA**（不带会 406）。

常用查询：

```
[out:json][timeout:90];
(
  node["natural"="peak"](S,W,N,E);
  node["natural"="saddle"](S,W,N,E);
  node["amenity"="place_of_worship"](S,W,N,E);
  node["place"~"village|hamlet|town"](S,W,N,E);
);
out body 900;
```

`ele` 标签经常有，可直接用作海拔。再补一条 `nwr["name"~"关键词1|关键词2"]` 做定向搜索（把攻略里出现的所有地名一次性丢进去正则匹配）。

**OSM 没有的地名**（本例：苏家宕、沙弥庵、千佛寺、药师殿、平坦寺）不要硬编坐标——要么用底图等高线估位并标注"示意"，要么在图上用虚线引导标出。

## 3. 轨迹：**优先真实轨迹，其次 OSM 测绘，最后才拟合**

**有 KML/GPX 就直接用真实轨迹**（全线实线，无虚线），做法见 **`references/track-prep.md`**。只有拿不到任何轨迹时才退到下面：

1. 拉步道网络：`way["highway"~"path|footway|steps|track"](bbox); out geom 4000;`
2. 建图：相邻点连边 + **按 45 m 容差合并断线端点**，边上权重取平面距离。
3. Dijkstra 串起锚点链。
4. **必须校验 snap 距离**：某锚点最近的图节点 >120 m，说明"步道不经过该点"，该段结果不可信，**要整段弃用**。

> 实干教训：不加 snap 校验时，最短路会在错误的地方"成功"返回——`天华峰→狮子峰` 报 `snap 2882/3057 m` 却返回 0 km 路径，把整条轨迹扯出一条 3.9 km 的跨山直线。

5. 覆盖不到的路段才用 Catmull-Rom 过控制点平滑拟合，并**只在此时**用虚实区分（实＝OSM 测绘/实测，虚＝走向示意），图例写明。**一旦拿到真实轨迹，就不要再保留任何虚线段。**

## 4. 拼接底图并叠加

```bash
python scripts/build_base_map.py    # → out/base_map.jpg + out/base_meta.json
```

要点：

- 用 Web Mercator，`lonlat_to_px(lon, lat, z)`，下载覆盖 bbox 的瓦片后按精确 bbox 裁剪，再缩放；
- **输出宽按"页面 CSS 宽度 × 2"取**（页面用 `--force-device-scale-factor=2` 出图），本例页面显示 730 px → 输出 1504 px，刚好 1:1 不虚；
- 存 JPEG q84（1504×3775 约 1.4 MB），base64 内嵌进 HTML 后约 1.9 MB，仍可接受；用 PNG 会到 5 MB+；
- `map_svg.py` 里用同一个 `projector(...)` 把经纬度投到**底图像素坐标系**，SVG 的 `viewBox` 直接写成 `0 0 图宽 图高`，于是 `<image>` 和矢量标注共用一套坐标，绝不会错位。

**版面比例必须守恒**：地图框的宽高比 = `lat_span / (lon_span × cos(中纬))`。南北向线路天然是竖长条（本例约 1:2.5），不要为了塞进横版而拉伸——改成**左侧竖地图 + 右侧信息栏**的两栏面板（本例 730 + 288），信息栏放分日图例、关键点海拔表、分段速查、底图来源，正好把留白填满。

**标注字号按底图像素给**：地图显示宽度 730 px 而 viewBox 宽 1504，缩放系数约 0.49，所以 SVG 里 `font-size=28` 渲染出来约 14 px。所有描边/halo 宽度同理放大。

## 7. 瓦片自带等高线太密/太淡：抹除 + DEM 自绘（贡嘎实战定案）

CyclOSM 的等高线问题在两个 zoom 上都无解：
- **z14**：1px 细线，高海拔浅色区几乎不可见（用户会说"等高线缺失"）；
- **z15**：密集一倍但仍是 1px 细线，陡坡区等高线像素占比 13–24%，视觉过密（用户会说"太密集"）。
且 z15 里**计曲线只占 0.04%**（腐蚀法无法分离保留），想"只留计曲线"的形态学筛选行不通。

**定案管线：抹除自带等高线 → 用本地 DEM 自绘** —— 已落成正式脚本
`scripts/tile_tint.py`（`python tile_tint.py --tile out/base_tile.jpg`；
自带 `--selftest` 合成图自检，不联网也能验"抹得干不干净"）。下面各步即它内部的实现：

1. **抹除自带等高线**（`tile_tint.erase_contours()`；逐块做则内存更友好）：
   - 色彩掩码：`r>140 & g>90 & r-b>50 & r-g>30 & b<210`（亮橙棕等高线+标注文字）；
   - **g>90 是关键**：排除深棕步道（CyclOSM 步道 g≈70），否则步道会被吃掉；
   - 掩码膨胀 1px（连抗锯齿边）后，**迭代邻域均值填充**（4 邻域有效值均值，~10 轮收敛）；
   - ⚠ 必须用 **edge-padding 取邻域**（`np.pad(mode="edge")`），`np.roll` 回绕会把对边像素
     填进边缘，接缝出现虚线点。自检合成图里这条是可测的：抹除率应 >95%、步道保留率应 >95%。
2. **自绘等高线**（AWS Terrain Tiles DEM，z15 原生 4.15 m/px，降采样后 marching squares）：
   - 间隔**不要写死**：用 `MT.pick_contour_interval(dem_out)` 按**实测线覆盖率 ≤30%** 自适应
     （2026-10-10 起，见 `pitfalls-terrain.md` §3）。经验值：攻略图幅（~7 m/px）常在
     **50/250 m**（长线）或 **20/100 m**（小窗口）落点，这两个都是"看得清线路又不抢戏"的区间；
   - 高程注记间隔跟着传：`MT.draw_contour_labels(..., every=计曲线)`；
   - 计曲线标注自动布点：沿计曲线段按间距撒点 + 最小间距去重 + 每 level 限 26 处。
3. **自绘颜色**：随 A 路线统一为**中性灰棕**（首 `(152,144,132)` α.36 / 计 `(100,90,80)` α.70，
   标注 `(96,84,72)` 白描边）。原 `#B9773F`/`#92591F` 暖橙棕会与暖色带撞成"发黄旧报纸"。

## 8. 浏览器渲染 SVG 地图的两次重采样坑

SVG `<image>` 内嵌 5120px 底图、viewBox 却是逻辑 1504 → 浏览器 5120→1504→5120 两次插值，
**细淡等高线被抹掉、晕渲发糊**（梯度能量损失 ~7%，主观"模糊/缺线"明显）。

修复：**高清出图时 viewBox 直接用底图原生像素**，`<image>` 1:1 不重采样，
矢量叠加层包一层 `<g transform="scale(raster_w/logical_w)">`（矢量缩放无损）。屏显 HTML 内嵌
（LANCZOS 一次降采样到 2048–2400）不受此坑影响。

## 9. 投影一致性：z 换挡后轨迹漂移

`projector` 若引用模块常量 `Z=14`，而 meta 已是 z15（scale=逻辑px/z15原生px）→
轨迹整体缩到左上角 1/4 区域。**规则：meta 里必须存 `z` 和 `bbox`，SVG 投影函数从 meta 读取，
禁止引用编译期常量。**（本技能已统一为 `guide_common.projector_of(meta)` —— z / bbox 一律从 `base_meta.json` 读，三处出图共用同一个投影函数。）

## 10. bbox 应紧贴线路（参考用户给的样图）

大 bbox 会浪费 30–50% 画幅在无关区域（如贡嘎主峰南侧冰川），路线被挤成小图。
**按轨迹+POI 外包矩形四周留 ~5.5% 边距**重切 bbox（瓦片缓存覆盖旧 bbox 时无需重新下载）。
注意边缘 POI 标签锚定方向要翻转（如右上角起点改 `dx=-34, anc="end"`），指北针挪到左上角避让。

## 11. 瓦片"一色米底"无地形感：DEM 分层设色 + 线画分离（贡嘎三轮定案）

用户诉求："地图基本一个颜色，无法给与地形参考"。直接把 DEM 设色半透明叠上瓦片会得到
泥浆色（瓦片米底 + 设色互相污染）。**正确做法是地形图标准管线——面积底色全部替换为
DEM 设色，只从瓦片里抠出"线画"保留**：

1. **线画掩码**（`tile_tint.lineart_keep()`）：
   - `line_m = clip((BoxBlur(7)亮度 - 像素亮度 - 5)/20, 0,1)`：比局部背景暗 → 线画（步道/文字/溪流）；
   - `hue_m`：偏绿(林地)/偏蓝(水体冰川) 按色相保留；
   - `keep = max(line_m, hue_m)`，输出 `瓦片*keep + 设色*(1-keep)`。
2. **高程-颜色 ramp**（要饱和，太淡会发泥）：2800 谷地绿(188,218,156) → 3400 黄绿 →
   4000 棕黄 → 4500 棕 → 4900 灰 → 5200 雪白；晕渲系数 0.80+0.40*shade（0.70+0.55 会压成泥）。
3. **雪线渐变**：smoothstep(4600→5050) 混向雪白，无硬边。
4. **快速迭代**：先拼一次瓦片存 `out/base_tile.jpg`，之后调色/调等高距只重跑
   `tile_tint.py`（读现成瓦片，秒级到十秒级），**不要重拼 2000+ 块瓦片**（可分分钟到十几分钟）。
   ⚠ 当时那段临时脚本会在 import 时解析 `sys.argv`，包装脚本得先清空 argv 再 import ——
   `tile_tint.py` 已把"拼瓦片"与"上色"彻底拆成两个脚本，不存在这个问题。
5. **图例入图**：SVG 右下无轨迹区画半透明白底图例（分日色条/符号/等高线/雪线渐变样本），
   字号 ~14.5px（逻辑坐标），比独立图例卡更省版面。屏显内嵌分辨率提到 2600px 保地名清晰。
6. 比例尺换算 `m/px` 的 z 必须取 `meta["z"]`，不要用 import 时的模块常量（换挡后差 2 倍）。

## 12. 自绘等高线"不能反映地形"：DEM→栅格映射三处系统性 bug（贡嘎实案）

用户反馈"等高线完全不能反映地形"，根因是 `draw_dem_contours` 的坐标映射错了，症状是
等高线被拉伸且整体偏移、与山脊沟壑走向不符。审映射时按此清单逐项核对：

1. **DEM 是否已裁到 bbox**：`load_dem` 返回的是裁好的 sub → dem(0,0) 就是 bbox 左上角。
   映射应为 `raster_px = dem_px * st * k`（st=降采样步长，k=raster_w/crop_w）。
   若误加 `-cx0,-cy0`（瓦片空间裁切偏移）会整体平移；若残留 z 换算 `2**(15-z)` 会放大。
2. **降采样步长别乘 2**：曾写成 `dem2x = 2*st`，等高线被拉宽 2 倍、密度翻倍。
3. **晕渲/设色与等高线必须用同一映射**：tint 直接把 dem 铺满 base（天然对齐），
   等高线若用另一套偏移，就会出现"设色与线不吻合"的精分现场。
4. **验证方法（务必做）**：把已知 POI（垭口/湖）按 meta 投影到栅格坐标裁图目检——
   鞍部应有闭合等高线贴着两坡、湖泊应有环绕盆地的线；以及对比同位置 hillshade 走向。

## 13. 性能复盘：一轮迭代为何耗掉 1 小时（贡嘎实测数据）

**实测耗时拆解**（replay_tint 单次 16–17 min，共跑了 2 次 = 34 min，占整轮 64%）：
- `contour_segments` marching squares：**513 s/次**（Python 逐格循环，2564×4677×20 levels ≈ 2.4 亿次格判定，87 万段输出）← 最大头
- DEM 加载仅 9 s（瓦片已缓存）；PIL 画 87 万段仅 ~1 s（C 实现，根本不是瓶颈）
- 其余：tint 合成/标注/5120px JPEG 存盘 ~5 min；label_points Python 遍历 87 万段若干分钟

**教训与优化（按收益排序）**：
1. **先验证映射再全量渲染**：等高线映射 bug（§12）本可 10 秒内发现——投影一个垭口坐标裁 800×600 小图目检即可；实际却跑完整图 17 分钟才被用户看出。规则：**任何映射/投影改动，先跑 <1 min 的 POI 裁片冒烟测试，再全量出图**。
2. **向量化 marching squares**：用 numpy 对 2×2 单元整体分类+插值（shift 数组布尔运算），预计 513 s → <10 s；退而求其次把 segs 缓存成 npz（键含 bbox/st/levels），重放零提取。
3. **探针脚本一次写对**：本轮验证脚本崩了 3 次（fetch_tiles_cyc import 吃 argv、build_route 返回的 pts 是 (lon,lat) 无高程、投影 y0 的 walrus 写错），浪费 ~8 min。规则：映射类探针一律从 `base_meta.json` 单一事实源推导；探针落盘成固定脚本（如 `probe_xx.py`，用完别提交）复用，不要每次 inline 重写。
4. **等待期并行**：17 min 后台渲染期间可同步做 HTML 图注/文档/技能回写，不要空等 TaskOutput。
5. 调参迭代务必走 base_raw 重放（§11.4），本次已受益——否则每轮 +18 min 拼瓦片。

## 14. 等高线"数值"核验（§12 管"位置"，这里管"高程值"）

自绘等高线后用户会问"数据对吗"。三层核验法（贡嘎实测）：
1. **POI 逐点对比表**：14 个 POI 取 `DEM 3×3 中值 vs KML 实测高程`，偏差应落在
   系统性小区间（贡嘎 +4~+44 m，均值 +29 m，σ=6 m——SRTM 雷达面 vs 气压计的典型差）。
   ⚠ 采样函数必须从 `meta["box"]` 扣裁切偏移，否则出现 +730 m 的假偏差吓自己（本次实踩）。
2. **独立高程点锚定**：图内知名峰（贡嘎主峰 7509 m / 中山峰 6886 m）与公开资料逐一核对。
3. **口径写进图注**："等高线基于 SRTM DEM，与轨迹实测（气压计）有约 +30 m 系统差，
   POI 以实测为准"——不然读者在垭口看到 POI 4894 m 紧邻 4900 m 等高线会以为标错了。
