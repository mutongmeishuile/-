## 1. 底图取源

- **默认自渲染底图，别等别人给瓦片**：`fetch_osm.py` + `make_terrain.py` 两条命令就能出一张真地形图，
  无速率限制、无版权风险、可无限重出。详见 `self-hosted-terrain.md`
  （含 DEM 源清单、Horn 晕渲、**等高线用 numpy 带边界栅格化**而不是 matplotlib、OSM 注记冲突处理）。
  用户点名瓦片服务时才走 `tile-basemap.md`。
- **换底图源先看合规再看好看**：官方 `tile.openstreetmap.org` **禁止批量下载**，别用；
  "OSM 地形图"实际是社区渲染（OpenTopoMap 最正统，CC-BY-SA，但要求不要 Massendownload）。
  一份攻略底图上千张瓦片就是"批量"，正解就是自渲染。`scripts/tiles.py` 已内置 `SOURCES` 多源切换表以备 B 路线。
- **Esri 地形图层在中国只到 z13**（z14+ 返回灰底占位图），`World_Hillshade` 才到 z16+。
  占位图检测用"缩到 32×32 后灰度标准差 < 2"，与源无关，**别靠 HTTP 200 或文件大小判断**。
- **别去硬刚风控**：两步路 `2bulu.com` 网页端有 SafeLine（雷池）WASM 挑战，
  构造指纹/解 challenge 既不稳也可能触发审批拦截；用户要轨迹就让他在 App 里
  「轨迹 → 导出 → KML」，比逆向划算得多。

## 2. 清晰度：放大看不清 ≠ 字号小

- **「放大看不清」要按超采样解，不是调大字号**：让底图栅格出 **2× 逻辑宽**
  （逻辑宽仍写进 `base_meta.json` 的 `size`，SVG 的 `<image width>` 用逻辑宽
  → 浏览器自动降采样 = 免费 2× 超采样），下游一行不用改。
  三个配套细节缺一不可：
  - **JPEG `subsampling=0`（4:4:4）** —— 否则彩色细线被 4:2:0 砍糊
  - **放大用 BICUBIC 别用 LANCZOS** —— 振铃会被 USM 放大成颗粒噪点
  - **USM 克制** —— `(3,55,4)` 起，别用 `(4,85)`
  详见 `self-hosted-terrain.md` §8。

## 3. 等高线

- **⚠ 等高距必须自适应，判据是「实测线覆盖率」而不是高程跨度**（2026-10-10 狼塔 C+V 定案）。
  等高线疏密 ≈ `每像素真实高差 / 等高距` —— **窗口越大，同样起伏被压进同样多的输出像素，
  每像素跨过的等高线就越密**，与"这座山多陡"无关。所以"比例尺越大等高线越密、地图越难看"
  是必然结果，写死一个间隔（如 20 m）只能对某一种窗口大小成立：
  - 亚丁大转山（0.19°×0.15°，z15）：20 m → 覆盖率 **21%**，像纸质地形图；
  - 狼塔 C+V（0.81°×0.62°，z13）：同一 20 m → 覆盖率 **66%**，整张图糊成一片棕。
  **正解：`pick_contour_interval(dem_out)` —— 从 `CONTOUR_NICE=(10,20,25,50,100,200,250,500)`
  由细到粗试，取第一个覆盖率 ≤ `CONTOUR_TARGET_COV=0.30` 的**。
  实测：亚丁仍取 20/100 m（细节不丢），狼塔自动退到 50/250 m（29.8%，可读）。
  高程注记的间隔必须**跟着传**（`draw_contour_labels(..., every=c_major)`），
  否则数字会落在没有加粗线的位置上，看起来"浮"在图上；且**只标计曲线**，
  首曲线也标就成"数字墙"。
  *（历史启发式 `跨度/80～100` 只在没有覆盖率数据时做粗估用，别当主判据。）*
- **⚠ 两个可调旋钮都在 `route_def.CFG`，别去动全局默认值**（2026-10-16 希夏邦马定案）：
  - `contour_target_cov`：本线路的覆盖率上限。希夏邦马 20 m 实测 **28.6%**（在默认 0.30 以内），
    但陡坡线仍成排、雪原上偏抢眼，用户要求"再细一些" → 收 **0.26** → 自动退到 **25 m（23.8%）**。
    **别把全局 `CONTOUR_TARGET_COV` 直接改成 0.26**：狼塔的 50 m 正好 29.8%，会被误判超限、
    继续退到 100 m（过疏）。全局默认留给"最坏情况仍可读"，收紧只在线路级做。
  - `contour_minor`：直接指定首曲线间隔、跳过自适应（不确定窗口时别用）。
  - `contour_cov_min`（2026-10-24 新增）：覆盖率**下限**。配了之后不是"越细越好"，
    而是在 **[下限, 上限] 区间里挑覆盖率最接近中点**的等高距 —— 疏密随地形自适应，
    但被夹在一个可读区间里（用户原话："线覆盖上限 20%、下限 15%，动态调整"）。
    区间内无候选 → 退到"≤ 上限里最接近下限的一档"；连最小间隔都超上限 → 取最粗一档并告警。
    不配下限则维持旧行为（≤ 上限取最细），**向后兼容**。
  - `contour_alpha` / `contour_min_delta`（2026-10-16 起）：只调**强度**不动几何。
    `alpha` = 线色与底图的融合度（默认 0.45 / 0.82）；`min_delta` = 线与底图的**最小明度差**
    （默认 15 / 34）。**dmin 越小线越贴底图**（容易记反：dmin 是"保证看得见"的下限）。
- **⚠⚠ "线太密"和"线太深"是两件事，分开调**（2026-10-24 十二条线批量实测）：
  | 症状 | 病因 | 对症旋钮 |
  |---|---|---|
  | 线**密**成网格纸 | **等高距太小**（自适应可能选到 10/20/25 m） | `contour_minor` / `contour_cov_min` |
  | 线**深**、抢眼、盖住山体 | alpha 大 + dmin 大（被强行拉开明度差） | `contour_alpha` / `contour_min_delta` |
  同一批线上"只降 alpha 不降 dmin"几乎没效果 —— dmin 会在中间调把线重新拉开。
  12 条线的自适应等高距实测差了 20 倍：冈仁波齐 **10 m**、南太行/大五朝台/七穿九变 **20 m**、
  冷龙岭 **25 m**、百错/K2/巴丹 50 m、天狼/南天山 100 m、伯舒拉岭 200 m。
  → **换线路时别信"默认自适应"，先看 `make_terrain` 打的「等高线 每 X m … 线覆盖 Y%」。**
- **⚠⚠ 覆盖率有两个口径，差 15–35%，判据必须用"实际像素"那个**（2026-10-24）：
  - `contour_coverage()` 是按 band 边缘的**估计值**；
  - `paint_contours()` 末尾打印的「线覆盖 X% 像素」是**实测值**（陡坡省略会减线、计曲线加粗会增线）。
  12 条线路两者比值 0.66–1.0（均值 ≈0.82）。双阈值判据若直接用估计值，
  用户配的 15–20% 落到图上只有 **9–13%**。故 `make_terrain` 用 `COV_EST_TO_ACTUAL=0.82`
  折算后再比较，打印时也报"预计实际线覆盖"。
  **报数据给用户时一律用实测值**（`线覆盖 X% 像素`）。
- **⚠ 沙漠线的等高线密度是地形本质，别硬压**：巴丹吉林沙丘链 25 m 一档就已经 24%，
  压下去沙脊就没了 —— 这种线应单独放宽上限，而不是全局改。
- **计曲线间隔用 `nice_major()` 推，不是死守 ×5**：
  首曲线 25 m 时 ×5 = **125 m 不是地形图规范值**（读数要写"125 的倍数"），
  而 ×4 = **100 m** 既在 `CONTOUR_NICE` 里、又是 25 的整数倍 → 注记间隔也回到 100 m。
  已经覆盖的映射：`10→50、20→100、25→100、50→250、100→500`（×5 优先，×5 不在 NICE 就试 ×4、×3）。
- **等高线宁细勿粗，且"提亮 + 收细 + 半透明融合"要一起做**：
  线一粗就糊成"棕色泥"。**首曲线与计曲线都取 1 px**（`CONTOUR_DILATE=(0,0)`）——
  粗细不再承担"分级"，改由线色的明度差承担（见下条）。
  *（2026-10-16 希夏邦马修正：计数线原为膨胀 1 次 = 3 px@3008，在**雪原**上一条条 3 px
  深灰线会连成"灰带"，把等高线读成色块而不是线 —— 本图 15% 是冰川/积雪白，必糊。）*
  另外**别再硬像素覆盖写色**（`rgb[mask] = 色值`）—— 1 px 上会留高反差硬边，
  是"旧地图感"的来源；改成 alpha 融合才有"印在纸上"的融合感。
- **⚠ 等高线颜色：两种错法，别在它们之间来回跳**（2026-10-10 狼塔 → 2026-10-16 希夏邦马）。
  1. **暖底图 + 暖线条 = 零色相差的"旧报纸"**：原配色暖橙棕 `(172,155,136)/(139,111,84)`，
     而分层设色本身就是"绿→土黄→陶土"暖色带 —— 只剩明度差，整张图发黄发闷。
  2. **改成"中性灰棕"只是把问题从"色相撞车"换成"色相无关"**：
     `C_MINOR=(152,144,132)`、`C_MAJOR=(100,90,80)` 全图一条色，
     可这一区是"谷地草绿 → 裸岩陶土 → 雪线以上冷白"，**线在冷白雪原上发脏、在草甸上发跳**，
     看图的直觉就是"颜色和这片地不搭"。
  → **正解：派生色（`CONTOUR_DERIVED=True`，`_contour_tint()`）——线色由该像素的底图色算出**：
    同色相 + 降饱和 0.30 + 明度分档（首 ×0.74 / 计 ×0.46），
    于是雪线上是冷灰蓝、草甸上是橄榄灰、裸岩上是暖灰，**线永远"长在地里"**。
    三条配套约束（缺一个就出问题）：
    - **暗处要反转成"提亮"**（底图亮度 < 110 时首 +16 / 计 +38）：阴影里的线若继续压暗，
      成排连起来就是"黑泥"，把晕渲的立体感吃掉 —— 这是固定色方案在背光面的老毛病。
    - **判据是明度差，不是颜色**：强制最小差值（首 ≥15 / 计 ≥34）；实测中位 36（首）/
      75（计）、p10 为 16 / 38，才"处处读得出线"。缩到 50% 仍可辨、放大 200% 层次不塌。
    - **alpha 反而要给足**（0.45 / 0.82，比固定色的 0.36 / 0.70 高）：色相已贴近底图，
      不必靠低透明去"躲"，否则收细成 1 px 后又淡到看不见。
  固定色保留在 `CONTOUR_DERIVED=False` 作为回退（纯色底图 / 只想出灰笔线时用）。
  高程数字色 `LABEL_FILL=(96,84,72)` 仍用固定深棕（数字要的是**可读性**而非"融进底图"，
  且带白色 halo），不必跟着派生。

## 4. 配色：分层设色 / 晕渲

- **⚠ 分层设色色带绝不能写死高程档位 —— 会静默退化成"一片单色"**。
  这是最隐蔽的一个坑：`hypso()` 里的 `np.clip(dem, stops[0], stops[-1])` 是**静默**的，
  色带走不出量程时不报错、不告警。实测把党岭的 3200–5400 m 档位原样搬到峨眉山
  （实测 461–3104 m），整个 DEM 被 clip 进最低一档 → 全图一个颜色，
  只剩晕渲在撑立体感，"分层设色"名存实亡（底图看上去"还行"，所以极难发现；
  发现它的办法只有一个：**把低海拔和高海拔两块各裁 1:1 出来对比底色**）。
  **正解：一条通用色带 + 按本区 p2–p98 拉伸铺满**（`_RAMP_*` + `ramp_stops()`），换地区自动适配。
  落地前先量 `np.percentile` 与各高程带面积占比，确认色带真的铺开了、没有被卡在某一档。
  另两个配套约束：
  - **无雪区不给雪色端**：色带末端用不用冷白，看本区有没有雪线（`SNOWLINE≈4300 m` 判据）。
    亚热带山体（峨眉山 470–3085 m）并没有常年积雪，涂成冷白是误导 → 顶端停在"裸岩陶土"。
    （有真雪线的高海拔线路另见 §5。）
  - **绿段要按线路实际停留的高程带加权拉长**：一条 46.8 km 里 40 km 都在 700–2100 m 森林带的线，
    若按线性色带铺，海拔刚过 1500 m 就转土黄 → 全图主色变棕黄，既不符合"这座山是绿的"，
    也会重犯"底图发土黄"的老毛病。让 0–0.55 都留在绿系，只有**接近山顶的裸岩带**才转陶土。
- **背光面压得太狠 = 整张图发脏**：`AMBIENT=0.62/DIRECTIONAL=0.45` 让背光只剩 0.62×，
  把偏灰的设色压成黑泥。抬到 `0.68/0.40`（背光 ≈0.68×、平地 ≈0.97×、迎光 ≈1.08×）立刻通透；
  再配一条**高光软限幅**（>240 的部分只留 35%），浅色档在迎光坡才不会被 clip 成死白面。
- **⚠ 单向晕渲"不够真实"：背光侧的地形结构会整片消失**（2026-10-10 用户问"如何更真实反映地貌"）。
  只从西北打一盏灯，迎光坡发白、背光坡糊成一团，冲沟/山脊/崖壁在暗部全部看不见 ——
  这不是"地形没细节"，是**光照模型丢信息**。
  **正解：MDOW 多向加权晕渲**（`MDOW=((225,.20),(270,.20),(315,.40),(360,.20))`）：
  主光仍取西北 315°（符合制图惯例、保住立体感），另补正北/正西/西南把暗部结构提出来。
  坡度加权（`FLAT_ANGLE`）只依赖坡度、与方位无关，权重和为 1 时**可以先合并再加权**，
  于是平滑/加权各只做一次，开销几乎不变。传具体 `az=` 仍退化为单向（保留旧行为便于对比）。
  代价：整体对比略降、3D"剪影感"变弱 —— 这是"真实 vs 立体"的固有 trade-off，
  攻略图取真实（细节由等高线补），要强立体感再单独调 `Z_FACTOR`。
- **阴阳分色（shadow tinting）—— 廉价但高效的真实感来源**：
  受光面微暖、背光面微冷（`TINT_WARM=.10 / TINT_COOL=.20`，冷色 `(0.90,0.95,1.04)`）。
  纯灰阶晕渲会让人潜意识觉得"纸是灰的"；加一点点色温差，山体立刻像有阳光与阴影。
  **幅度必须小（≤0.25）**，大了就成"蓝紫色的假雪"。不需要就设 `0 = 关闭`。
- **平原"起云"不是噪声，是真地形，别用"多模糊一点"解决**：垂直夸张会把 30 m DEM 的微起伏
  一起放大（横纵向高频能量实测只差 1.5 倍）。按**真实坡度**加权（`arctan(tan_slope)`，未夸张）
  —— ≥2.5° 全保留、<2.5° 渐回平地基准 —— 才是外科手术式的解法。
  另注：PIL 的 `GaussianBlur` **不支持 `"F"` 模式**（抛 `image has wrong mode`），
  要模糊浮点明暗值请用"降采样 → `Image.BOX` → 升采样"。
- **面要素（林地/草坡）用"乘法染色"替代"平铺半透明色罩"**：色罩是恒定颜色，
  既留多边形硬边又把晕渲整块抹平（OSM 的 wood 面常是粗略勾的大块区域，一硬就特别扎眼）。
  正解是画进独立 `"L"` 掩膜 → 大半径高斯羽化（≈10 逻辑 px）→ 对底图乘法着色（压深 + 转青绿），
  **必须在合成矢量层之前做**，否则连道路一起染。
- **不是每个语义都要占一个色相，明度也是一条通道**：公路原本用高饱和橙黄
  （观感像 2010 版谷歌图，且与米黄/奶油杏地形撞色），改成**白芯 + 暖灰棕描边**后靠明度浮起来，
  还顺手把橙黄通道腾空给实测轨迹。详见 `legend-and-color.md` §1 与 §6。
- **底图注记与攻略 POI 重名时要抑制底图那条**：两边海拔口径会打架
  （OSM 十王峰 1344.4 vs 实测轨迹 1345.5），同图两个数会让人误判。
  `draw_osm.draw_overlay(..., skip_names=)` 传入 POI 名集合即可，
  `make_terrain.py` 会自动从 `route_def.POIS` 取。
- **中国境内线路的分区配色另见 `references/china-terrain.md`**（森林/草原/荒漠/高寒/
  盐湖的目标色与色序）。⚠ 记住一条边界：**那里的绝对高程色阶只作"色序"参考，
  档位一律走本节的 `ramp_stops()` 分位归一化**，抄绝对档位 = 复现本节首条的"一片单色"。

## 5. ⚠ 高海拔线路：色带要「偏白 + 冷色雪线」

暖色系会把雪画得不像雪。用户问「底图配色是否可以偏白色」时，**答案是可以，
而且雪线主题的图应该偏白**。

暖色带（米黄→杏→陶土→玫瑰棕）在冰川线上有两个硬伤：
1. **语义错**：4 座冰川达坂 + 冰原被渲成浅陶土/玫瑰棕，读者看不出「这是雪」；
2. **层次糊**：2900–4300 段色相差太小，40%+ 的高海拔面积糊成一整片。

**正解（三原则）**：
1. **低海拔草绿一路带到 3000 m**（植被语义不能丢，也是全图的对比锚）；
2. **中海拔靠「绿→黄绿→浅米」的明度阶梯拉层次**（每档明度差 ≥20），不靠色相；
3. **3700 m 起去饱和转冷，3800 m 进雪线用冷白，4100 m 以上近纯白** ——
   雪线成为画面上唯一高亮区，与实测轨迹的橙红形成冷暖对比。

**⚠⚠ 踩过的坑：转白不能只提明度**。第一次尝试把 2600–3800 全推成灰白
（明度 198→222），结果 42.8% 的高海拔面积糊成一片「雪盲」，山形全部丢失，
灰蓝等高线数字也因底太浅而读不出来。**必须同时保住明度阶梯。**

**改色带后必须同步改四处**（漏一处就色调打架）：

| 项 | 暖色带 | 冷白带 |
|---|---|---|
| 等高线 | `(172,155,136)／(139,111,84)` 暖灰棕 | `(158,162,168)／(120,126,135)` 冷灰 |
| 等高线 alpha | 0.55 / 0.86 | 0.50 / 0.78（白底对比本就强，不必压重） |
| 高程数字 | `(105,79,55)` 暖棕 + 纸色描边 | `(96,104,116)` 冷灰蓝 + **纯白**描边 |
| 晕渲 `A/D` | 0.70 / 0.38 | **0.76 / 0.32**（白底上阴影绝对差被放大，不抬就整片发灰） |

南天山北线实测色带（可作高海拔线起点，再按本线分位微调）：
```
1700 (158,200,170) / 2100 (186,218,172) / 2600 (208,222,178) / 3000 (220,224,184)
3400 (226,218,190) / 3700 (218,214,200) / 3800★(220,224,228) / 4100 (234,240,246)

```

> **中国境内线路另见 `references/china-terrain.md`**（三大自然区染色目标色、
> 中国色序、特有地貌与水体）。⚠ 那里给的**绝对高程色阶只能当"色序"用**，
> 档位仍走本节的 `ramp_stops()` 分位归一化 —— 直接套绝对档位就是本节首条的"一片单色"。

### 5b. ⚠⚠ 雪线以上「又是白的又是绿的」：`belt_stops` 的植被锚点是绝对高程（2026-10-17 北天山）

用户原话：「渲染的雪线之上怎么又是白的又是绿的」。

`belt_stops()` 里混了两组锚点，只有一组是通用的：

| 组 | 锚点 | 性质 |
|---|---|---|
| `alpine` | `s−1300 … s+2100`（高寒草原→草甸砾石→砾石→裸岩→季积→**雪线白**→峰顶冰雪） | **雪线相对**，任何区域成立 |
| `veg` | `0 / 2900 / 3400 / 3900 / 4300`（森林深绿→针叶林→灌丛→灌丛草甸→高原草原） | **绝对高程**，按喜马拉雅型高雪线区域的谷底调的 |

雪线一低，`veg` 就窜到雪线以上，把刚转白的积雪带又插回灌丛绿/草原绿。北天山（雪线 3800 m）实测的色带走向：

```
3800 m  (232,235,240)  雪线白
3900 m  (138,158,118)  灌丛草甸绿   ← 雪线正上方发绿
4200 m  (242,244,249)  又白回来
4300 m  (150,172,132)  高原草原绿   ← 又绿
4800 m  (247,248,252)  再白
```

于是图上是「白→绿→白→绿→白」的断层。**希夏邦马（雪线 6000）/ 念青东（5000）最高锚点 4300 都在雪线以下，旧色带在雪线以上本来就是全白的** —— 这就是同类线路一直没暴露的原因。

**修法**（`make_terrain.belt_stops`）：任一 `veg` 锚点**严格高于雪线**时，把整组按比例收进 `[dmin, s−1300]`，顺序与相对间距不变；收编分支内做同高程去重（顶锚点会正好落在 `s−1300` 上）。

⚠ **阈值故意卡在"高于雪线"，不是"进入高山带"**。念青东（雪线 5000）最高锚点 4300 落在雪线以下的高寒草甸带，旧色带雪线以上全白（占画面 30.8%）—— 为它重算是白改一条已交付线路。**只修真出问题的**，改动前先跑一遍逐米新旧色差对比确认零回归。

**验收判据**：不能只看"图上没有明显绿块"，要量化 —— 取 DEM ≥ 雪线的像素，算 `绿度 = G − (R+B)/2 > 15` 的占比。北天山修复后雪线以上 14.4% 的画面里只剩 **0.09%**（等高线/JPEG 噪点级别），中位色 RGB(214,215,220) 即积雪白。

### 5c. ⚠ 切边扫描对深绿林区线路会假报警；判据是轨迹完整性，不是抬阈值

同一个修复的副作用：植被顶锚点收编后正好落在 DEM 谷底，最低档「山地森林深绿」`(104,124,96)`（亮度 ≈115 < 120）叠加晕渲后整片露在边缘，`qa_guide` 切边扫描 top 冲到 **44%**，越过 0.40 —— **但内容一点没裁**（轨迹四边余量 104–3682 px）。

⚠⚠ **别用"继续抬阈值"消警**（0.40→0.50→…），那是把真裁切一起盖掉 —— 这类自检最常见的死法。
正解是把既定口径真正实现（§5 注释里早就写了"满幅底图只能靠尺寸+轨迹完整性判断"，
但代码只抬了阈值）：`qa_guide.edge_scan(full_bleed=True)` → `track_inside()` 读
`out/track_full.json` + `base_meta.json`，把轨迹投影回画布算四边余量：

- 余量全 ≥ 0 → 判"完整"，深色占比只作提示；
- 出现负余量 → **真裁切**，窗口/投影要查。

反向验证必须做：把成品图裁掉一半喂回去，`track_inside` 要给出负余量并判失败
（实测裁高 2000 → 下余量 −1210；裁宽 700 → 右余量 −700）。**只验正向会得到"永远通过"的检查。**

## 6. 雪线高程：查资料定，不能凭感觉

这是用户会问的高频问题。四步：

1. 从轨迹数据算出**本线最高点**与各阈值以上的里程占比；
2. 联网查该山段雪线（多源交叉）；
3. 按**坡向 + 所属段**取值；
4. **把结论写进攻略正文**（`.snowline` 样式块）**并在地图图例加一条双色块样本**。

**天山参考数据**（多源交叉）：

| 来源 | 雪线 |
|---|---|
| 天山山区遥感雪线监测（2001–2015） | 山区平均 **3975 m**；北坡 3900 m；伊犁河谷段 3600 m |
| 中国天山南/北坡雪线区间 | 南坡 3900–4200 m / **北坡 3500–3900 m** |
| 各段实测 | 西段别珍套山北坡约 3600 m、东段博格达山北坡 3860 m |
| 天气网 | 天山整体 3600–4400 m |

夏塔段（昭苏，伊犁河谷南侧、天山西段北坡）→ 取 **3800 m 为雪线下界、3900 m 为稳定积雪界**。

**⚠ 常见误区：别把「轨迹最高点」当雪线。** 南天山北线最高 4100 m 而雪线 3800 m —
**全程大部分路段在雪线以下**，只有翻达坂与冰原短段在上。这个结论本身对读者最有价值。

**天山以外的山脉取值查 `references/china-terrain.md` §4**（阿尔泰 3000–3200、祁连 4300–5240、
念青唐古拉 4500–5700、横断 4600–5500、喀喇昆仑 5100–5400、冈底斯 5800–6000、
喜马拉雅南坡≈4500 / 北坡 5900–6000）。⚠ 雪线由**降水**主导而不是纬度或海拔，

**⚠ 换线路时 `snowline_m` 和它的文案必须一起配**（2026-10-17 通用性复核发现的真 bug）：
`_snowline_from_cfg()` 只覆盖**高度**，`SNOWLINE_LABEL` / `SNOWLINE_NOTE` 原本是模块级常量
写死着上一座山的米数 —— 于是出现"虚线画在天山 3600 m、图上却写『北坡雪线 ≈6000 m』"
这种图文打架。现已改为 `_snowline_texts(level)` 按实际 level 生成，
并与 CFG 形成三级优先：`CFG['snowline_label']` → 模板 → 自动 `雪线 ≈{level} m`；
副注 `CFG['snowline_note']` → `CFG['snowline_src']`（自动包括号）→ 空。
→ 换线路**四个键一起配**：`snowline_m` / `_label`（含坡向）/ `_note`（另一坡）/ `_src`（真源头）。
  **只改高度不改文案是最危险的** —— 它不报错，图上也不会露馅，只有懂这片山的人看得出。
→ 另外：没配 `snowline_m` 时会打 ⚠ 提示"沿用脚本残留默认值"，看到就去查表，
  别让它安静地画错。低海拔线路（主峰远低于雪线）应当**删掉雪线配置**而不是留着默认值。
不要写 `f(纬度)` 公式，只能按山脉（必要时按坡向）查表取值。

高亮说明块的写法（含 CSS 行宽与类名避坑）见 `references/pitfalls-layout.md` §5。

## 7. 改色 = 多处同源一起改

- **改底图配色 = 三处同源一起改**：`make_terrain.py`（设色/等高线/晕渲常量）
  ↔ `draw_osm.py`（矢量常量）↔ `build_guide.py`（图例常量 & `.snowline` 文案），
  漏一处图例就指向旧色。改完必须按
  `make_terrain → build_guide → shoot_guide → render_map_hi` 的顺序重跑。
- **地图窗口绝不写死**：`make_terrain.py` / `fetch_osm.py` / `build_base_map.py` 三处
  **都调 `guide_common.resolve_bbox()`**（内部 = 轨迹包围盒 + 35% 留白，可被
  `route_def.CFG["bbox"]` 覆盖）。旧版三处各写一份 `LON0/LAT0/LON1/LAT1` 常量，
  改一处忘另外两处 → **矢量与底图整体错位**；更糟的是新线路忘了改 → 直接把上一座山渲出来，
  **而且完全静默**（页面照样"有山有水"）。
  → 现在开工前 `assert_bbox_covers()` 会校验轨迹落在窗口内，越界即 `SystemExit`。
  改纬度会同时改画布宽高比 → 见 `pitfalls-layout.md` §1（反解地图比例）。
  **"窗口画错山"的排查手法**：看 `out/base_meta.json` 的 `bbox` 是否贴着轨迹的经纬度范围
  （差半度以上就是串了），或直接按 `tx0/ty0/z` 反算窗口中心经度对不对。
- **底图重渲染要跑 `make_terrain.py`（约 2 分钟）**，改色带/窗口后必须重跑；
  下游 `build_guide → shoot_guide → render_map_hi` 全部要跟着重出。
- **长图之外要另给一张独立高清地图**：攻略页里地图受版式限制只有 ~1163 设备像素宽，
  **长图放大必然糊**。把同一份 `map_svg.build_svg()` 按底图原生宽（如 3008）另渲染一张 JPEG。
  见 `scripts/render_map_hi.py`。
- **内嵌底图与高清图不能共用一个降采样上限**：`build_svg()` 为控 HTML 体积把底图降到 1600 px，
  而 `render_map_hi.py` 复用同一函数时若不解除该上限，高清图就被"高清"了个寂寞。
  用 `build_svg(embed_max=0)` 显式关闭。

## 8. ⚠ 空洞判据必须「单边偏低」——写 `abs()` 会把真峰顶填平（2026-10-09 亚丁大转山）

AWS Open Data 的 terrarium z15 瓦片可能带 SRTM 空洞（某次实测 10 片），解码后直接出现
**负海拔**（实测 `−5362 m`），高程范围一崩，分层设色整条色带就全错。

**判据演进（每一步都是踩坑踩出来的）：**

1. ❌ `median ± 2500 m`：真实谷底就有 3285 m，1736～2500 的空洞**落在合法区间内**被放过。
2. ⚠️ `abs(dem − ref) > VOID_MAD`（局部参考面判据）：能抓住低值空洞，**但同时把"高出
   参考面 400 m 的真实峰顶"一起判成异常**。亚丁线实测：被判 58293 px"空洞"，
   其中 **57882 px 都在 4000 m 以上、最高 5934 m —— 那正是仙乃日/夏诺多吉/央迈勇的峰顶**。
   填完后全域最高点从 **5935 m 掉到 5661 m**，三座 5000+ 山峰被削成平滑穹顶，
   在图上就是 **"山顶一块没有等高线、边缘生硬的平板"**（用户一眼看出来的就是这个）。
   而且**全程不报错、高程 min/max 也"看起来正常"**，极难察觉。
3. ✅ **正解：单边判据** —— 真实空洞（缺数据）只会**偏低**，不会偏高：

   ```python
   bad  = (ref - dem) > VOID_MAD          # 只有"远低于局部参考面"才算空洞
   bad |= ~np.isfinite(dem) | (dem < med - 2500)   # 坏瓦片（整片 0 / 负值）兜底
   ```

   `VOID_MAD` 取 **900 m**：既抓住负值/零值坏瓦片，又不会被 400–700 m 的真实峰顶误伤。

**两个配套推论：**

- **terrarium 其实常常没有空洞**。亚丁线单边偏低异常 = **0 px**，正确行为是"一个都不填"
  （打印"无空洞，跳过填充"，别为了填而填）。
- **大空洞（数千～数万 px）别在全分辨率上迭代**：4 邻域 Jacobi 每轮只扩散 1 px，
  600 轮 ≈ 25 px 半径，空洞内部喂不到，最后落到兜底中位数上 → 又是一块平板。
  改分尺度：**1/4 分辨率迭代 900 轮 → BICUBIC 上采样 → 全分辨率 120 轮抹缝**，
  得到的是平滑穹顶而不是平板。

**自检（写进流程，别只靠眼睛）**：填完后 `max(dem)` 应与 `load_dem` 打印的原始最高点
**一致**（除非确实有坏瓦片）；不一致就是误填了真地形。

### 8a. ⚠⚠ `VOID_MAD=900 m` 只适用于「小窗口」；500 km 级大窗口会填掉 25% 的真地形（2026-10-17 尼泊尔四线总览）

四线全景（4.56°×1.39°，DEM z12 13282×4593 px）实测：单边判据报出 **15 336 171 px = 25.14%**
"空洞"，全部填成中位高程 4354 m —— 地图下半部变成一块**没有起伏的死绿平板**
（缩略图上像"海岸线"一样的不规则边界，正是调和插值穹顶的边缘）。

根因：判据是「低于 1/6 分辨率参考面 900 m」。参考面在 1/6 尺度上等价于 ~80 km 平滑，
而喜马拉雅**深切河谷本来就比山脊低 4–6 km、水平距离只十几公里** —— 整条南部低地
（1854 m 以下，占窗口 25%）一律命中。同一个数字在小窗口（亚丁 0.19°）里是安全的，
一换到区域图就是灾难。

**判据（按窗口跨度选）**：

| 窗口 | 能不能用 `ref − dem > 900 m` |
|---|---|
| 单条线路（≤ 0.3°，~30 km） | ✅ 可以（原行为不变） |
| 区域/多线总览（≥ 1°，~100 km+） | ❌ **改成只填真 NaN + 负值夹 0** |

大窗口的正确写法（本图落地）：

```python
bad = ~np.isfinite(dem)          # terrarium 在本区 NaN 常为 0%
d[bad] = med; d = np.maximum(d, 0.0)   # 负高程只可能是坏瓦片，夹 0 即可
```

**先量后填**：跑 `np.isnan(dem).mean()` 与 `(dem < 0).sum()`。若 NaN=0%、负值只有几十个，
就说明**没有真空洞**，任何"参考面"判据都只会帮倒忙。判据的失败长相是"整块地形失去起伏"，
不是高程 min/max 异常 —— min/max 看起来完全正常（0–8753 m），只有看图才发现。

## 8b. ⚠ 色带顶端不要取 p98：峰顶会被 clip 成一块纯白平顶（2026-10-09 亚丁）

`ramp_stops()` 原用 `p2–p98` 拉伸色带。亚丁线 **p98 = 5263 m 而最高峰 5935 m** ——
**p98 以上 2% 的像元（三座雪山的峰顶）全部 `np.clip` 到同一个顶色**，
表现同样是"山顶一块没有等高线的平板"（配合 §8 一起出现，很难分清是谁的锅）。

正解两条一起用：

1. 拉伸上界改 **p99.7**（被截像元从 2.00% 降到 0.30%）；
2. `ramp` 里 `TOP_F = 0.93` 以上那一段（近雪线 → 雪白）**单独拉伸到全域最高点**：

   ```python
   stops.append((hi + (f - TOP_F) / (1.0 - TOP_F) * (dmax - hi), col))
   ```

   于是峰顶是 **连续渐变的雪帽**（雪线色 → 冷白），而不是一块平白。
   `ramp_stops` 里顺手打印 `dmax` 与顶格像元数，方便一眼看出还有没有被截平的峰顶。

## 9. ⚠ Overpass 镜像会集体阵亡：先探活再定序，别按"名气"排

`fetch_osm.py` 的 `MIRRORS` 原本按名气排序（de → kumi → jp），实测有一轮**三个全灭**：
`overpass-api.de` 持续 **504**、`kumi.systems` **500**、
`overpass.osm.jp` 直接 **SSL 证书域名不匹配**（这是硬失败，重试毫无意义）。

- **正解：换成 `overpass.osm.ch`（瑞士站），一次就通**；`overpass.private.coffee` 作为第二备。
  两个 CDN 稳定的站放前面，主站 de 退到第三（它繁忙时就是 429/504 的来源）。
- **证书不匹配的镜像要从列表里删掉**，不要留着"占一个轮次"——它永远不可能成功。
- 出门前先探活（几十秒，省掉后面几分钟的连环超时）：

  ```bash
  for h in overpass-api.de overpass.osm.ch overpass.private.coffee overpass.kumi.systems; do
    printf "%-26s %s\n" "$h" "$(curl -s -o /dev/null -w '%{http_code}' -m 12 "https://$h/api/status")"
  done
  ```

  返回 `200` 才值得排进 `MIRRORS`。
- 抓完**别急着 `--force` 重抓**：`out/osm.json` 是缓存，只有改了窗口才需要重抓。
- **更要紧的是：抓不到不该让流水线挂掉。** OSM 矢量只是底图的一层装饰 ——
  没有它，地形晕渲 + 等高线照样出图。所以 `fetch_osm.py` 加了 `--soft`：
  全镜像 × 多轮都失败时，写一份 `{"elements": []}` 空缓存并 **`exit 0`**（打印醒目降级提示），
  而不是 `SystemExit`。`make_all.py` 通过 `STEP_ARGS = {"osm": ["--soft"]}` 默认这么调它。
  实测一轮 4 个镜像全体 504/500（含 osm.ch），正是靠这条降级，整条流水线才没在 wave1 断掉。
  → 判据：**只有"不可替代"的步骤才允许失败即中断**（prep / dem / html），装饰性步骤一律可降级。

## 10. 底图注记抑制要按「核心地名」匹配，不能只比全名

`route_def.POIS` 的名字常带后缀（`万佛顶 · 全程最高`、`雷洞坪 · 观光车终点`），
而 OSM 的注记是裸地名（`万佛顶`、`雷洞坪`）——**全名比对不成立**，
结果底图上并排出现两条同地注记，看着像两个地方。

正解（`make_terrain.py` 已内置）：除全名外，把 **`·` 之前的核心地名**也加进 `skip_names`。

```python
skip = set()
for _p in POIS:
    skip.add(_p[0])                            # 全名
    skip.add(_p[0].split("·")[0].strip())      # 「·」前的核心地名
```

自检口径：`make_terrain.py` 会打印 `抑制重名 N`，**N 应该是 1~3 而不是 0**
（为 0 说明一个都没抑制上，重名注记大概率还在图上）。

## 11. ⚠ 底图 OSM 注记（地名/峰名/湖名/水系名）看不见、或几乎全丢（2026-10-09 亚丁）

用户原话：「底图中可以取原始 osm 图层的地名/山峰名/湖泊名/水系等名称，动态标注在合适位置」。
现场症状是**图上一条 OSM 注记都没有**，而 `draw_osm.py` 其实一直在画 —— 三个原因叠加：

**① 字号按「1:1 看高清图」定，没按「缩进长图」定。**
底图会同时被 ① 长图/网页按 ~0.35–0.45 倍嵌入、② 高清图 1:1 看。
原来峰名 11.5 px，缩到长图里只剩 ~4 px，**等于没有**。
→ 全线上调约 1.35 倍（峰名 15、地名 14.5–18、水系 13.5、兴趣点 13），
  颜色加深（峰名 `(58,40,26)`）、描边加粗到 2.6–2.8。判据：**与等高线高程标注同一量级**。

**② `Labeller` 撞上等高线标注就直接 `return False`（静默丢弃）。**
等高线高程标注先占用网格（104 个标注 ≈ 10% 单元，而且**恰好密集在山脊/峰顶**），
峰名/湖名本来就在同一片区域 → 实测 **15 个山峰名只画出来 2 个**。
→ `place()` 改成**三级**：① 原位置无冲突 → 放；② 按 10/18/28 px 的 8 个方向找无冲突位 → 放；
  ③ 全都挤 → **取冲突最少的那个位置也要放**（`fallback=True`）。
  地名被压在等高线数字上顶多是拥挤；**整条名字消失是信息缺失**，两害相权取其轻。
  ⚠ 但**兴趣点（viewpoint/attraction）保持 `fallback=False`** —— 它们价值低，
  强行塞进去反而会压住攻略自己的标注（本线实测「仙乃日观景点」压在「珍珠海」上）。

**③ 只画峰名/地名，没画湖名与水系名。**
→ 新增 `waters` 收集：`natural=water` / `landuse=reservoir` 的**面**（锚点取顶点重心）、
  `waterway=*` 且带 `name` 的**线**、以及 `natural=water` 的**点**；
  用深青蓝 `(36,84,128)` 居中放置，仍走 `Labeller` 动态避让。
  本线效果：山峰名 12/15 · 地名 4/4 · 水系名 12/14。

**④ 底图注记 vs 攻略标注的"互相打架"。**
底图注记画在栅格上，攻略 POI 标注随后叠在 SVG 里、**还带白描边** ——
两者一撞，底图那条会被白描边啃掉半行（现场：「仙乃日」被「珍珠海」压住）。
→ `make_terrain.poi_label_cells()`：按 route_def 的 `dx/dy/anchor` 与同款字号粗算每个
  标注框，换算成 `draw_osm` 的**禁标网格**（cell = 14×SS）一起 seed 进去。
  ⚠ 网格单元是**栅格像素**，而 proj 已经乘过 `scale_raster` —— 别再乘一次 `ss`，
  否则禁标区会被放大到整张图（实测山峰名立刻从 12/15 掉到 2/15）。

**自检**：`draw_osm` 每次打印 `山峰名 x/N · 地名 x/N · 水系名 x/N`，
**山峰名落位率 < 60% 就说明避让策略又过严了**（正常应在 80% 上下）。

**⑤ OSM 名里的藏文/天城文等 PIL 字体画不出，整条标签变成豆腐块□□□（2026-10-16 希夏邦马）。**
西藏线路的 OSM `name` 常带藏文（`扎青村 སྦྲ་ཆེན`）或天城文（`युब्रा`），
PIL **没有字体回退**，画不出的字形全部渲染成黑框，比不画更难看。
→ `draw_osm._clean_name()`：收集阶段就过滤，只留 CJK / 拉丁 / 数字 / 常见标点
  （` ·-—–()（）.°'’&,+/~`）；整名都在集之外的（纯藏文/天城文名）直接弃用。
  ⚠ 必须在**收集阶段**清洗，`skip_names` 匹配与出图才会用同一套名字；
  若只清洗绘制那一行，抑制重名会先于清洗失效。
  同类线路（珠峰东坡 / 希夏邦马 / 亚丁等藏区线）必踩，症状是"村名后面跟一排黑框"。

## 12. ⚠ 冰川面 / 峰点注记 / 时令河：三处「按数据量级做地图学分级」（2026-10-16 希夏邦马）

这一线把 OSM 的 `natural=glacier`（382 个面，占图幅 **15.2%**）、`natural=peak`（191 个点）、
`waterway=stream`（333 条，其中 79 条 `intermittent=yes`）都抓了回来。
**数据量一大，旧实现的"有就画、画不下也画"就直接崩掉**，三处都踩了：

**① 冰川边界画了近白色 → 白边界压在白雪地上，等于没画边界。**
踩的写法：`C_GLACIER_ED = (238, 247, 253)` —— 大概是为了"别太抢眼"。
但雪线以上的地形底图**本身就是积雪白**，近白边界完全不可见，冰川范围读不出来
（现场：一条条冰舌和雪原糊成一片，只有下界在岩色上勉强看得出）。
→ 填充可以"近白淡蓝"（`(224,237,249,150)`，比雪原略冷一档），
  **但边界必须是可读的冰蓝 `(118,168,210)`**，宽 1.4 px。这是把冰舌"勾"出来的唯一手段。
  ⚠ 填充透明度别拉到 165+ ：冰面下的晕渲（冰瀑、裂隙场）对登山线是有用信息，
  压没了就只剩一片白。实测 150 是"读得出冰"与"看得见起伏"的平衡点。
  ⚠ 冰川面**两层都要真画**：`way` 直接成环，`relation` 要遍历 outer member 的 geometry
  （`out geom` 才带 geometry，抓取语句里必须有 `relation["natural"="glacier"]`）。

  **⚠⚠ 但这一层**技能默认是关的**（`draw_osm.DRAW_GLACIER=False`；要开必须按线路
  在 `route_def.CFG["glacier_layer"]=True` 显式打开，见 `_cfg_flag`）** ——
  上面的"边界要可读"是**开着的时候**怎么画对，不等于**该开**：
  - 冰川面占图幅 **15.2%**，那层"近白淡蓝 alpha 150"的填充**等于给整片雪区打了层雾**，
    冰瀑、裂隙场、雪面起伏全被压平 —— 而这些恰恰是登山线要看的地形信息；
  - 关掉后，冰雪范围并没有丢：**雪线以上的积雪白（DEM 派生）+ 等高线**已经说清楚了，
    多一层冰川面是重复表达，还赔上地形起伏。
  - 判据：**数一数有多少冰川末端伸到雪线以下**（雪线白盖不住的才值得单独画）。
    冰川范围 ≠ 雪线范围时才有必要开。实测两例：**希夏邦马**（冰川几乎全在雪线以上，
    与雪线白重复）→ 关（默认）；**贡嘎**（93 块里 **76%** 末端下探雪线以下，海螺沟末端低到
    2980 m 的季风海洋型冰川）→ **开**。
  - 开/关都在**线路级** `CFG["glacier_layer"]`；别去改 `draw_osm.DRAW_GLACIER` 常量
    （那等于把某一条线路的判断写死进技能）。
  - 关层要**连带改三处**，否则自相矛盾：① `glacier_layer` 不写或 `False`（面与冰川名一起关，
    注记循环也包在同一个 `if` 里）；② 删掉图例里的"冰川"行（`CFG["legend_extra"]`）
    —— 图例写着却没有的图层，比不画更糟；③ 图注（`CFG["map_note"]`）里
    "浅蓝面为冰川（OSM）"这句必须删，改成"冰雪范围由高程渲染"。
  - 副产物：关掉后**切边扫描会报警**（底部深色占比 22.6%→33.0%），见 §13 末条。

**② 峰点注记不分级 + 不排序 → 主峰没名字、无名矮峰有名字。**
踩的写法：遍历 `peaks` 直接 `lab.place(..., fallback=True)`。
两个后果：i) 191 个峰点实测画出 **102 个**峰名，山体区被注记糊死、等高线数字全被压住；
ii) `fallback=True` 是"实在放不下也要放"，而遍历顺序是 OSM 返回顺序 ——
一座 4300 m 的矮峰会**先**占掉 7000 m 主峰需要的空位，出现倒挂。
→ 两条一起改：
  - **按 `ele` 降序排**（`ele` 常带单位，写成 `float(str(s).replace("m","").strip())`，解析失败给 `None` 排最后）；
  - **分三级**，但阈值必须是**本窗口峰点高程的分位数**（`PEAK_TIER_PCT=(88,62)`），
    ~~不能写绝对米数~~（2026-10-17 修正：原先写的 `≥7000 / 6500–7000 / <6500 m` 是
    希夏邦马的值，搬到武功山 1918 m、亚丁 6032 m 会让**所有**峰落进最低档 ——
    主峰不突出、还不保证占位，等于把"主峰没名字"这个 bug 在低海拔线路上重演一遍）。
    改相对分级后本线实测 **p88≈7010 / p62≈6518**，与原绝对阈值近乎等价，
    且在"整个分布平移"的低海拔窗口上仍能自适应。
    有效高程样本 < `PEAK_TIER_MIN_N`(=8) 时不分级、一律中档（分位数在小样本下不稳）。
    并 `fallback=False`（只填空位）。实测 102 → 89 个，且**49 个是真正的地标**，
    被挤掉的全是背景矮峰。符号（▲）也跟着分大小，小峰用浅一档的棕色。
  ⚠ 别用"峰名落位率"当唯一指标：这个教训恰恰说明**落位率高不代表对**，
  该丢的要丢（参考 §11 的自检口径：落位率是防"全丢"，不是要求"全画"）。

**③ 时令河和常年河画成一样的实线 → 给出错误的水源信息。**
`waterway=stream` + `intermittent=yes` 是冰川融水冲沟，**旱季断流**（本线 333 条里 79 条，24%）。
徒步攻略里"一根蓝线＝一处水源"是默认读法，画成常流水会让人按图找水。
→ `intermittent=yes` 走**虚线 + 细一档**（`_dashed(..., 7*S, 6*S)`，色 `(152,192,222)`），
  并在路线图例里**单列一行**（`CFG["legend_extra"]`）说明"仅暖季有水"。
  图例不写等于没画 —— 读者看不出虚线的意思就是"季节性的"。

**这一节的通用结论**：OSM 给的是**要素的绝对数量**，而地图要的是**信息层级**。
面要素（冰川占 15.2%）看**占比**决定要不要加边界/纹理，
点要素（191 个峰）看**分布密度**决定分级，线要素（24% 是时令）看**属性构成**决定线型。
抓全数据 ≠ 全画上去，中间那一步才是制图。

## 13. ⚠ 注记字号是"两头夹"出来的；治重叠靠留白，不靠缩字号（2026-10-17 希夏邦马）

**① 字号有下界也有上界，不是一个方向调到底。**
- 下界（2026-10-09 亚丁）：11.5 px 的峰名缩进长图（~0.4×）后完全看不见 → 当时整体放大 1.35×；
- 上界（2026-10-17 希夏邦马）：本窗口 191 个峰点 + 30 个水系名 + 11 个地名同屏，
  18 px 地名 / 16.5 px 峰名在 1504 px 逻辑画幅上互相挤压
  → 用户原话"图中标注的字体缩小，避免重叠" → 再收 **0.85×**。
- 结论：**13–15.5 px（逻辑）是这一族底图的可用区间**。动手前先分辨这次反馈是"嫌小"还是"嫌挤"——
  两个方向的历史教训都在上面，来回调的代价是每次 30 s 重渲染 + 用户再提一轮。
- 配套：点位符号跟着收一档（地名圆点 3.0/2.4 → 2.7/2.2，兴趣点 2.6 → 2.4）——
  字缩了而圆点不动，视觉上会"头重脚轻"。峰顶三角不缩（它是定位锚点，缩了读不出峰位）。

**② 真正治重叠的是留白（`LBL_PAD`），不是字号。**
字号缩 15% 只让单个注记面积降约 28%，两个注记仍可能贴边；而留白直接改变"能不能挨着放"
的判据 —— 冲突面积按**周长**算，留白是平方级收益。`LBL_PAD` 由 2.0 → **2.8**（乘 S）。
⚠ 别超过 3.2：山脊上峰名本来就挨着等高线数字，留白给太大 → 大量注记被丢弃（落位率反而降）。

**③ "有没有重叠"需要一个可测口径：`Labeller.n_overlap`（挤放数）。**
`place()` 里那条 fallback 分支（"实在放不下也要放"，见 §11）每命中一次就 +1，
verbose 打印 `· 挤放 N`。**落位率高 ≠ 排得好** —— 可能全是挤出来的，只有这个数能区分。
本线实测：字号 ×0.85 + 留白 2→2.8 后，峰名落位 89 → **92**（字小了反而多放下 3 个，
因为白描边占的格子小了），挤放 15 / 133 个注记 ≈ 11%，集中在峰群密集处。
⚠ 别指望挤放归零：把 fallback 全关掉，就是重演 §11「15 个峰名只画出 2 个」。

**④ 满幅底图的"切边报警"是误报 —— 阈值要单独放宽。**
`qa_guide.py` 的切边判据是"最外 2 px 亮度 < 120 的占比 > 阈值"。但底图**铺满画幅**、
没有留白边框时，边缘天然压在地形上：背光坡、深谷、等高线数字全会被算成"深色"。
实测关掉冰川层（那层近白填充本来等于给雪区提亮）后，bottom **22.6% → 33.0%**、
left **21.4% → 28.0%**，越过 0.30 阈值直接报警；而此时尺寸仍是底图 3008×4904、
轨迹未溢出 —— **内容并没有被裁**。
→ 全线地图阈值放宽到 **0.40**，并明确口径：满幅底图类产物，切边只能靠
**尺寸 + 轨迹完整性**判断，深色占比只作粗略提示；有留白的产物（长图）仍用 0.02。
（先确认"不是真裁"再放宽阈值 —— 直接调阈值把真问题盖掉，是这类自检最常见的死法。）

## 14. ⚠ 两张图"地名/山峰名差很多"：先分清**数据源稀疏**还是**脚本漏抓**（2026-10-17 念青东）

用户原话：「相比希夏邦马，缺少很多地名，山峰名，湖泊名，水系名等」。
第一反应（用户的和模型的都是）是"技能没同步"，**逐字节比对三个位置后确认脚本一致**。
真正病因是 **OSM 在那个窗口的数据本身就稀** —— 和技能无关。

### 诊断三步（按顺序做，别跳）

1. **`out count` 比窗口**：直接问 Overpass 这个 bbox 有多少个目标要素。
   念青东窗口（95.70–96.27E，30.12–30.46N）`natural=peak` = **1**；
   希夏邦马窗口 = **191**。
2. **比 `osm.json` 的命名元素清单**（`tags.name`/`name:zh` 非空的元素数）：
   念青东 **42** 个，希夏邦马 **193** 个。到这一步就能下结论。
3. **大范围密度对照**（确认不是窗口选歪了）：
   念青东大区（29.5–31.5N / 94–97E，约 22 万 km²）= 299 个 peak；
   希夏邦马—朗塘大区（27.5–30N / 84–87E，约 15 万 km²）= 1866 个 peak。**密度差 6 倍**。
   结论：非登山区（念青东、横断山腹地）OSM 峰点就是极少，**这是数据源现实，不是 bug**。

### ⚠⚠ 最大的坑：`overpass.osm.ch` 里没有亚洲数据（会把"稀疏"误判成"没数据"）

诊断查询**必须用全球镜像**（`overpass-api.de` / `kumi.systems`）。
osm.ch 是瑞士区域实例，查亚洲 bbox 会返回 `total: 0`，
且 `osm3s.timestamp_osm_base` 是个 1970 年的秒数（`117785`）—— **这是判据**：
正常值应是 `2026-xx-xxT…` 这样的日期串。本次实测：同一个 bbox 的 peak 查询，
osm.ch 返回 0，overpass-api.de 返回 1（真实值）。
→ 用 osm.ch 做"这里没数据"的结论 = 冤枉了数据源。`fetch_osm.py` 的 MIRRORS 列表里
osm.ch 排第一位只是**抓取**时最稳（它对中国区返回空会触发要素数下限校验自动换镜），
**诊断**必须换主站。

### "脚本漏抓"那一侧确实也有两个漏项（本次已修）

| 漏项 | 症状 | 修法 |
|---|---|---|
| `natural=saddle`（哑口/垭口）没抓 | 非登山区 `natural=peak` 常常为 0，**saddle 是那一带唯一稳的山口标注来源**，却整类漏掉 | `fetch_osm.py` 查询加 `node["natural"="saddle"](bbox)`；`draw_osm.py` 加分支：倒三角 ▽ + 名 + ele，用 warn 橙，与峰名的 ▲ 区分；`fallback=True`（垭口是线路必经点，重要性高于一般地名） |
| `place=locality` 没抓 | `place` 正则只到 `hamlet/suburb/neighbourhood`，**小地名整类消失** | 正则补 `\|locality`。念青东实测补回 3 个：腊风、郎角玛、半得里 |

念青东实测增量：元素 367 → 373，地名 13/15 → 15/18，哑口名 0 → 2/3（第三个无名）。
⚠ 增量通常很小（OSM 稀疏区补不出东西），**别指望这一步把密度拉到希夏邦马水平**。

### 音译差异会画出重名（腊丰 / 腊风、巴巴拉 / 巴拉拉）

同一个村子 KML 叫"腊丰"、8264 攻略叫"腊风（巨石旁）"、OSM locality 叫"腊风"；
同一个垭口攻略叫"巴巴拉垭口"、OSM saddle 叫"巴拉拉垭口"。
`skip_names` 是**全串精确匹配**，"腊丰巨石旁营地" ≠ "腊风" → 两个都画，
同一处两个标签必然互相挤。
→ route_def 配 `OSM_SKIP = ["巴拉拉垭口", "腊风"]`，`make_terrain` 把它并入
`skip_names`（2026-10-17 新增的通用钩子）。**图上只保留本线 POI 那一个名字**。
（念青东实测：哑口名 1/3 → 0/3、地名 16/18 → 15/17，抑制生效。）

### 补地名的主通道是 route_def 的 POIS，不是 OSM

OSM 到顶之后，还能补的是**公开攻略里的地名**（两步路 / 8264 / 马蜂窝正文）。
念青东从攻略补回的有：赫巴董牧场、巴巴拉错、无名错营地、小措营地、通参牧场、

定位办法：攻略给"当日营地高程"，KML 注记点给"里程 + 高程"，**两者高程对得上就认为是同一处**，
并在 route_def 注释里写明推定依据（例如"攻略 D4 无名错营地 4800 ↔ KML #9 营地 4817 @40.07 km"）。

### ⛔ 不能给 OSM 无名湖硬安名字

2. **峰名按"图上间距"去重，不要按单一高程阈值**。判据：

### 8a-2. ⚠⚠ 「坏瓦片兜底」`dem < med − 2500` 会把高海拔窗口的低谷整片抹平（2026-10-17 昆布 / 干城章嘉）

这次只有 0.03% 像素命中「低于参考面 900 m」，真正动手的是 `bad |= dem < med - 2500` 这条兜底。
昆布窗口高程**中位 4837 m** → 阈值 2337 m → 1800–2337 m 的整条河谷（28.9 万 px，1.58%）

判据：`med − 2500` 这个"绝对下限"是**相对窗口中位数**的，窗口越高、谷底越低，越容易误伤。
只要窗口的 中位数 − 最低点 > 2500 m（喜马拉雅南坡、横断山深谷基本都满足），这条兜底就是定时炸弹。

```python
bad |= ~np.isfinite(dem) | (dem < 0)      # ✅ 坏瓦片只表现为 NaN / 负高程
```

**量一遍再改**（这两条命令能把"配色不够"和"被抹平"分开，别靠猜）：

# ① 到底填了多少、填在哪
out = fill_voids(dem); diff = np.abs(out - dem) > 0.5
print(int(diff.sum()), 100 * diff.mean())            # >0.5% 就要警惕

## 16. ⚠⚠ 晕渲光照方向：坡向公式在图像坐标系里会被「镜像」（2026-10-20 贡嘎大环）

**症状**：用户说「谷底看起来更像山脊」。放大看，每条沟都是"中间亮、两壁暗"。
山体的阴坡阳坡全反，但**等高线完全对得上、脚本不报错、所有数值自检全绿**。

**根因**：`aspect = np.arctan2(dzdy, -dzdx)`。
图像坐标系 y 轴向下，这个写法把坡向沿 45° 轴**镜像**了 —— 北坡算成东坡、东坡算成北坡。
主光设的是西北 315°，实际照到了东南 135°。

**判据（唯一可靠）**：不要看"像不像"，算统计量：

```
面向西北的坡 亮度 0.293  ←  应该亮
面向东南的坡 亮度 0.787  ←  应该暗    ✗ 反了
```

修好后是 `西北 0.797 / 东南 0.283`。差值必须 ≥ +0.25。

**修法**：
```python
aspect = np.arctan2(-dzdx, dzdy)     # 北0° 东90° 南180° 西270°
```
自检脚本已固化成 **`scripts/check_hillshade.py`**（读 `out/base_meta.json`，退出码非 0 = 光反了）。
换任何线路都先跑这一条，**比看一万次渲染图都靠谱**。

**为什么镜像会造成"谷底像山脊"**：镜像不改变坡度，只把"受光墙"和"背光墙"对调。
一条谷本应是"一壁亮一壁暗、谷底居中"，镜像后受光的那面墙跑到同侧的两条沟之间，
视觉上就连成一条亮脊 —— 人眼对"亮=凸"极其敏感，一眼就看出不对。

> 💡 反推：凡是"地形看着不对劲但等高线没错"的问题，先查光照（方向 / 明暗配比 / 雪区处理），
> 再查色带。等高线是几何事实，它跟 DEM 永远对得上，**不会骗人**。

## 17. ⚠ 雪线以上别用「回抬」抹平晕渲（2026-10-20 贡嘎大环）

**症状**：`snowline_m` 配得低的线路（贡嘎 5100 m、峰顶 7509），雪线以上那一大片
（占图面 1/3 以上）是"一张白纸 + 等高线"，主峰群完全没有立体感。

**成因**：老实现的 `snow_w` 是**回抬**到"无山影的设色"：
```python
snow_w = clip((dem - snow_m) / 600, 0, 1) * 0.6     # ❌ 把雪面晕渲压掉 60%
img = img * (1 - w) + rgb * w                        # 回到扁平设色
```
本意是"山影别把雪涂灰"，但峰顶设色本身已经接近纯白 (250,251,254)，
两者叠加 = 没有任何明暗信息。

**修法**：方向反过来 —— 雪面用**更强的**明暗塑形：
```python
snow_w = clip((dem - snow_m) / 500, 0, 1) * 0.85
shaped = clip(rgb * (0.58 + 0.60 * hs), 0, 255)      # 环境光 0.58 / 方向光 0.60
img = img * (1 - w) + shaped * w                     # 受光近白、背光中灰
```

**验收口径**（别靠眼睛）：取一片雪坡（无文字、无粗线），`GaussianBlur(5)` 后算标准差
→ **应 ≥ 35**；回抬版只有 ~30，肉眼就是白纸。

**连带**：`AMBIENT, DIRECTIONAL = 0.66, 0.46` → **`0.60, 0.50`**。
原配比下 `amb + dir*hs` 只在 0.79–1.0 之间变化，明暗差 21%，整图发灰；
现在是 0.70–1.00。别再往下降环境光（<0.55 背光面会成黑块、压掉等高线）。

**为什么别的线路没暴露**：`snow_w` 只在雪线以上生效。格聂（雪线 5000、主峰 6204）
窗口绝大部分在雪线以下，几乎没走到这条分支；贡嘎雪线以上有 2400 m 高差才炸出来。
**雪线配得越低、主峰越高，越必须验证这一条。**

## 18. ⚠ 分层设色的带位必须**单调**：混用「绝对米数」和「雪线偏移」会折返（2026-10-20 贡嘎大环）

**症状**：用户说"色阶过渡又黄又绿又黄"。听上去像主观感受，实际是可测的配色错误。

**成因**：`belt_stops` 的锚点一半写绝对高程（3900 / 4300），一半写 `s - 1300`。
雪线 5100 时 `s-1300 = 3800 < 3900`，排序后色带序列变成：

```
3800 黄绿 → 3900 绿 → 4100 黄 → 4300 绿 → 4400 棕      ← 来回折返
```

**修法**：带位**一律按雪线的比例**定位（0.50 → 1.00），等比缩放永不穿插：

```python
anchors = [(0.50, ...), (0.58, ...), (0.66, ...), (0.72, ...), (0.78, ...),
           (0.84, ...),  # 高寒草原，全带最黄的一点
           (0.88, ...), (0.91, ...), (0.94, ...), (0.965, ...), (1.00, 雪白)]
raw = [(s * f, c) for f, c in anchors]
```

**自检**（已固化成 `_ramp_check()`）：用 `G - R` 衡量绿度，越正越绿、越负越暖。
雪线以下必须**单调递减**，任何一段回升 > 6 个色阶就是配色错误并打印高程区间。
旧版 `4100→4300` 回升 +20，一眼就能定位。

**顺带记住这条色相顺序**（从谷底到雪线）：
森林深绿 → 灌丛 → 草甸 → 高寒草原（最黄）→ 草甸转砾石（黄转土）→ 流石滩 → 裸岩（最暗）
→ 岩雪混杂（转中性灰）→ 雪白。
**明度可以中途下沉（裸岩本来就暗），但色相的"绿度"不能回头。**

## 19. 一张"看着不对劲"的地图，排查顺序（2026-10-20 贡嘎大环一天内连修 6 个问题后的总结）

按这个顺序查，每一步都有**可量化的判据**，不要凭感觉改参数：

| 症状 | 先查什么 | 判据 / 工具 |
|---|---|---|
| 地形看着不像立体 | ① 光照方向 ② 雪区处理 ③ 光比 | `check_hillshade.py`（NW 亮 ≥ SE +0.25）→ §16；雪坡 std ≥ 35 → §17；`amb/dir` 应在 0.60/0.50 |
| 谷底像山脊 / 阴坡阳坡反 | 光照方向（坡向公式镜像） | 同上，§16 |
| 一片白 / 一片褐，没有过渡 | 色带单调性 | `_ramp_check()`：雪线以下 G−R 不得回升 >6，§18 |
| 密布"布纹" | 等高线在陡坡的像素间距 | `线间距 <6 px` 就要软减淡；<45° 不画首曲线，§3 |
| 一块块硬边色块 | OSM landuse 面 | 透明度 ≤62、羽化 ≥2×ss，`pitfalls-map-svg` §19 同源思路 |
| 字压字 / 字压线 | 两套注记是否共享占位表 | 导出 `label_boxes.json` + `_OCC`，`pitfalls-map-svg` §19；峰簇看 §20 |
| 图例位置怪 | 位置是否写死 / 占位表是否漏登记家具 | 动态选位 + 把指北针、比例尺也登记，`pitfalls-map-svg` §16 |

**贯穿全程的两条元经验**：
1. **"看着不对但几何没错" → 一定是渲染参数，不是数据。** 等高线永远和 DEM 对得上，它是几何事实，
   拿它当基准去反推，能立刻排掉"数据错了"这条错误假设。
2. **每个视觉问题都要落成一个可测的数字**（亮度差、std、覆盖率、像素间距、框数）。
   否则改完只能"看着好像好点了"，下一轮又复发。

## 20. 季节档：**技能默认就是夏季地貌**（2026-10-20 定案）

`make_terrain.py` 顶部：

```python
SEASON = "summer"            # 技能级默认；CFG["terrain_season"]="annual" 可回退
SUMMER_SNOW_SHIFT = 350.0    # 夏季雪线上移量（米）
```

**为什么默认夏季**：徒步季就是 6–10 月，图上就该是那时的地貌 —— 草甸是绿的、季节性积雪已经退掉。
按"年常态"出图会把雪线画在 3800 m，而夏季实走的 3800–4200 m 全是草坡，图上却是一片白，
读者会误判"这段要过雪线"。

**两条实现细节**：
1. 偏移加在 `build_terrain` 里（`snow_m += SUMMER_SNOW_SHIFT`），**不是**加在 `belt_stops` 内部 ——
   这样雪线虚线、分层设色、雪面塑形三处**天然用同一个值**，不会出现"线在 3800、白从 4150 开始"。
2. `belt_stops` 的 `season` 参数只控制**调色板**（夏季植被更绿更饱和），不控制高程。
   两个旋钮分开，才不会又出现"色带锚点与雪线互相穿插"那类折返（§18）。

**判据**：日志里必须出现
`季节档 summer：雪线 3800 → 4150 m（+350 m，夏季季节性积雪已退）`，
且随后的 `色带自检：雪线以下 G−R 单调递减` 不报错。

⚠ 例外：**沙漠线路**（腾格里等）本来没有雪线，走 `terrain_palette="desert"` 分支，
季节档对它无影响；南半球/反季节线路（如 12 月出图）按需设 `"annual"`。


## 21. ⚠⚠ 扩大地图窗口：显式 bbox 的正确取法、代价，以及"换窗口 = OSM 缓存作废"（2026-10-21 珠峰东坡）

## 25. 必须显式写 `snow_month: 7`，否则雪线偷偷跑成 10 月档（2026-10-23 两条线实测）

**本工作区所有线路的统一口径是「7 月初出图」→ `CFG["snow_month"] = 7`（ELA −150 m）。**

但 `snow_month` **不是默认值**：不写就落到 `SUMMER_SNOW_SHIFT = 350`，
也就是"10 月档"（新雪回来、视觉雪线最高）。两条新线（子龙秘境 / 雅拉温泉海子线）
2026-10-23 就是因为漏了这个键，图例和底图注记一度按 10 月写。

各月偏移（`MONTH_SNOW_SHIFT`，`snowline_m` 定义 = 8–9 月的现代雪线 ELA）：

| 月 | 5 | 6 | 7 | 8 | 9 | 10 |
|---|---|---|---|---|---|---|
| 偏移 | −500 | −350 | **−150** | 0 | +200 | +350 |

所以：

| 线路 | `snowline_m`（ELA） | 漏配 `snow_month`（错） | 配 `snow_month: 7`（对） |
|---|---|---|---|
| 子龙秘境 | 4970 | 5320 | **4820** |
| 雅拉温泉海子线 | 5100 | 5450 | **4950** |

底图烤进去的那行注记（`snowline_label` 格式化后）用的是**右边这个值**；
`short` 字段只在 `legend_outside=True` 的三段式图例带里用
（`map_svg._legend_band_items()`），也必须是右边这个值。
图内图例用的是 `desc`，一般不带数字 —— 那里不存在"图文打架"，但带数字就必须写实际值。

**做法**：配完 `snowline_m` 与 `snow_month` 一定要看 `make_terrain` 这两行 ——
`月份档 7 月：雪线偏移 -150 m（相对现代雪线）`
`季节档 summer：雪线 5100 → 4950 m（-150 m，仍处残雪期，雪线低于平衡线）`，
把 **右边那个数**填进 `legend_extra[i]["desc"] / ["short"]`；
文案照抄历史线路的写法：`desc = "≈4950 m · 7 月档（ELA 5100 −150 m）..."`。

更稳的写法（两条线都用这个口径，读者也不会懵）：

- `snowline_label = "10 月雪线 ≈{:.0f} m"`（标题里点明季节）
- `snowline_note  = "（季节性积雪已退，冬季下移到 ≈<配置值> m）"`
- `legend_extra[0]["short"] = "10 月雪线 ≈5450 m"`（填**实际值**）
- `legend_extra[0]["desc"]  = "以上为常年积雪与冰川（10 月线）"`

⚠ 判据：地图上蓝虚线的位置 vs 图例里的米数。两者差 350 的时候，
图面上"雪线"会明显高于图例说的那条 —— 这是唯一的肉眼判据，自检不报错。

⚠ 另外：配置值本身要用**冰川末端中位 / 顶部中位**交叉验证（§4），
不能沿用别的山。雅拉实测 3 块冰川末端中位 5019 / 顶部 5259 → 取 ≈5150（配 5100）；
子龙 19 块 4788 / 5157 → 取 ≈4990（配 4970）。

## 26. ⚠⚠ OSM 地名标注点必须落在**地物本身**上（2026-10-24 十二条线批量修）

**症状**：图上"桑曲"三个字指着几公里外的空地；湖名落在湖外；村名飘在半山。

**根因（量化，别靠肉眼）**：底图注记的锚点用**要素顶点的算术质心**。
直线要素没问题，但**弯曲 / 分叉的河，质心会落到河道外面**。
实测（百错千寻窗口 8 条具名水系）：质心离河道距离**中位 320 m、最远 5955 m**；
"桑曲"标签实际偏了 223 逻辑 px（成图 ×3 = 669 px）。
面状要素（湖/水库/冰川）同理：环质心对**凹形**湖可能落在湖外。

**修法**（`draw_osm.py`，commit `388c003`）：
- 线状要素（水系、道路）：锚点 = **离质心最近的线上点**（垂足）→ `_nearest_on_polyline()`，
  必然落在要素上；
- 面状要素（湖/水库/冰川）：锚点 = **多边形内部的点** → `_anchor_in_ring()`：
  质心在面内就用质心，否则取离质心最近的边并向内收一点（`_point_in_ring()` 射线法判内外）；
- 点要素（place 村 / POI 寺 / peak 峰）本来就是 OSM 节点坐标，**精确，不动**；
  峰另走 `peak_snap` 吸附 DEM 山顶（名字跟着吸附后的位置走）。

**度量技巧（可复用，不靠肉眼）**：用 OSM 要素几何直接算"锚点到该要素的最短距离"：
经纬度空间做局部平面近似（`kx=111320·cosφ`, `ky=110540`）+ 点到线段距离，
统计中位/最大值即可定位偏差来源。改完再算一遍，距离应为 0。

⚠ **改 `draw_osm` 必然改底图 → 必须重跑 `make_terrain`**，
否则 HTML / 长图 / 高清地图还在用旧底图（症状：只有独立 JPG 变了，页面没变）。
⚠ 标签文字本身仍可能被避让挤开几 px（此时画 0.5 px 细引线指回锚点）——
这是制图常规，**不影响"指哪儿"**；要标签也必须紧贴就得收紧外扩档位，代价是地名变少。

## 27. ⚠ `terrain_season="annual"` 时 `snow_month` **不生效**（2026-10-24 冈仁波齐）

`make_terrain` 只在 `terrain_season == "summer"` 时做月份修正。
配了 `terrain_season="annual"`（为了避开"植被带上移把高原染绿"的问题）时，
**`snow_month` 写了也不会被读** —— 雪线就是 `snowline_m` 的原值。

两种做法二选一：
- 保留 annual：**把 7 月折算值直接写进 `snowline_m`**（如 6000 → 5850），
  并在注释里写明"annual 档不自动修正，故直接写折算值"，别留 `snow_month` 造成误解；
- 改回 summer 档：能吃到月份修正，但要注意 `belt_stops` 的植被顶端会随之上移
  （summer 档 `s−700`，annual 档 `s−1300`），干旱高原可能被整片染绿。

判据：看 `make_terrain` 打的「月份档 N 月：雪线偏移 …」这行**有没有出现**。
没出现 = 走的 annual，月份键被忽略。
