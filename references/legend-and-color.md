# 图例与配色：一张地形底图怎么才"读得出来"

自渲染底图把等高线、水系、路网、注记全画在一张图上之后，**真正的难点从"画出来"变成"分得开"**。
这份文档只讲两件事：**色相怎么分配**、**图例怎么画**。全部结论来自一次真实的返工（九华山南北穿越）。

---

## 1. 配色：按色相分通道，不要按明度

### 踩过的坑（原话：「小路与整体配色接近，不易识别」）

步道最初用了两种色：

| 尝试 | 颜色 | 结果 |
|---|---|---|
| ① 浅棕 | `(150,106,72)` | 直接消失在山体的赭石色里 |
| ② 深棕（接近墨色） | `(86,58,44)` | 压得住底色了，但**和计曲线 `(126,100,72)` 同色系** —— 等高线一密，步道就"长"成了等高线，两者谁也认不出 |

**根因**：两次都在调**明度**，而底图上已经有一个棕色家族（分层设色 + 首曲线 + 计曲线）。
只要还在棕色里找，就永远是"深的棕"对"浅的棕"。

### 正确的做法：先划色相，再定明度

把整张图的色相通道先分完，再往空位里塞（下表是**第二轮返工"底图配色美化"之后**的最终值）：

| 色相 | 归谁 | 值 |
|---|---|---|
| 青绿 → 黄绿 → 米黄 → 杏 → 陶土（连续） | **地形本身**（分层设色） | 见 §6，晕渲后自然形成 |
| 棕（暖灰棕、半透明融合） | **等高线**（首 / 计） | `#AC9B88`@.55 / `#8B6F54`@.86 |
| **白芯 + 暖棕描边** | **公路 / 村道** | 芯 `#FFFCF6` + 边 `#B28A6A`（第二轮由橙黄改此） |
| 蓝 | **水系**（溪流 / 水体） | `#6096C8` |
| 绿（乘法染色，非色罩） | **林地 / 草坡** | 底色 ×(0.91, 0.945, 0.878) + 羽化 |
| **紫（深）** | **步道 / 小径** ← 唯一空位 | `#743482` + 纸色虚线描边 |
| 橙红 / 蓝（高饱和、粗） | **攻略主线路 D1 / D2** | `#E4572E` / `#1E6FD9` |

> 地形底图的"底色家族"是绿—米黄—杏—陶土（暖色连续带）。可用的空色相只有 **紫 / 品红 / 青**。
> 青会和溪流抢，所以步道用**深紫**。这是唯一稳的解法。
>
> **第二轮的额外发现**：橙黄原本分给公路，但高饱和橙黄的观感像 2010 版谷歌图，
> 且与 700–900 m 档的米黄/奶油杏地形直接撞色。公路改成**白芯 + 暖棕描边**之后：
> ① 白色是全图唯一的高亮中性色，在**任何**一档地形上都能靠**明度**浮起来，不依赖色相；
> ② 色相通道进一步腾空，实测轨迹（橙红）不再有竞争者；③ 道路层级改由线宽 + 描边深浅表达
> （这本就是纸质地形图的做法）。**结论：不是每个语义都必须占一个色相 —— 明度也是一条通道。**

### 光换色相还不够：加纸色描边把线"抬"起来

地形底图是**中灰调**的（不像 OSM 标准图那样纯白底），细线压上去天生缺对比。给步道叠一层**纸色虚线描边**：

```python
_dashed(d, pts, C_TRAIL_CASING, W(w) + 2, dash, gap)   # 先画：纸色 (252,250,245)
_dashed(d, pts, core,           W(w),      dash, gap)   # 后画：深紫芯
```

**关键：两遍的 `dash/gap` 必须完全一致**，缺口才会对齐 —— 看起来是"一条有轮廓的虚线"，
而不是"两条错开的虚线"。`draw_osm._dashed(..., casing=, casing_w=)` 已经把这件事封好了。

### 自查清单

- [ ] 把图缩到 25%，**不问"好不好看"，问"能不能指出哪条是步道"**。指不出来就是配色失败。
- [ ] 把图缩到 25%，还能不能区分"等高线"和"步道"？这两条最容易撞。
- [ ] 主线路（橙/蓝）与所有底图元素都不同色相？步道深紫 vs 主线橙红——够分。
- [ ] 有没有哪个色相承担了两个语义？（棕色一肩挑"地形+等高线+曾经的步道"就是崩点）

## 2. 线宽：主线路的"粗细"是相对量

用户反馈原话：「标注的轨迹太粗了」。原来是 `stroke-width=7.5` + 白描边 `14`。

调参经验（逻辑坐标系，`viewBox` 单位）：

| 项 | 原值 | 现值 | 说明 |
|---|---|---|---|
| 主线路芯宽 | 7.5 | **5.0** | 缩到攻略页（~581 CSS px）约 2 CSS px，一眼找到又不挡地形 |
| 白描边宽 | 14 | **8.0** | **描边别做成芯宽的 2 倍**——那会读成"双白边"，比线本身更显粗 |
| 5 km 里程点 | r=9.5 | **r=7.4** | 线细了，点必须跟着收 |
| 点位符号 | r=19 / 20 | **×0.85** | 用一个 `PS = 0.85` 系数统一乘，别一个个改 |

> **改线宽一定要连带改符号尺寸**。线细了而点没变，视觉层级会反过来（点压线），
> 用户下一次的反馈就会变成"点太大"。一个 `PS` 系数统管全组是最省事的做法。

## 3. 图例：样本必须由「同一套参数」生成

### 别用色块 + 文字糊弄

反例（本次被替换掉的旧图例）：

```html
<div class="rlg"><i style="background:#BFBFBF"></i><span>底图细线＝OSM 步道 / 公路</span></div>
<div class="rlg"><i style="background:#7B5A3E"></i><span>等高线数字＝该线高程（m）</span></div>
```

问题：**「细线」到底多细？「#7B5A3E」是哪条线？** 读者得回到图上自己找。
图例存在的唯一理由就是省掉这一步 —— 要指认的东西恰好是这张图最需要讲清的（步道 vs 等高线），
结果图例本身含糊，等于没写。

### 正解：样本内联 SVG，参数与出图代码同源

```python
def _lsw(stroke, width=3.6, dash=None, casing=None, casing_w=None, w=32, h=16):
    """线状样本。casing 与芯线用同一 dash 串，缺口对齐（＝真实描边效果）。"""
    y = h / 2
    da = f' stroke-dasharray="{dash}"' if dash else ""
    o = [f'<rect x=".5" y=".5" width="{w-1}" height="{h-1}" rx="3.5" fill="#FFFDFA" stroke="#EDE6DC"/>']
    if casing:
        o.append(f'<line ... stroke="{casing}" stroke-width="{casing_w}" ...{da}/>')
    o.append(f'<line ... stroke="{stroke}" stroke-width="{width}" ...{da}/>')
    return f'<svg width="{w}" height="{h}" viewBox="0 0 {w} {h}">{"".join(o)}</svg>'
```

三条要点：

1. **颜色常量只在一处定义**，图例与出图脚本共用。本次的对应关系：
   `make_terrain.py`（底图常量）↔ `draw_osm.py`（矢量常量）↔ `build_guide.py`（图例常量）——
   **改一处要同步三处**，这是这套架构必须付出的代价，所以在三处都写了同样的注释。
2. **点位样本直接复用出图用的符号工厂**：`_psw(kind)` 内部调 `map_svg.mk_pin(0,0,kind)`，
   包一个 `viewBox="-21 -21 42 42"` 就完事（半跨度 21 才装得下最高峰带白圈的那个符号）。
   **绝不为图例另画一套符号**——那必然会和图上不一致。
3. **双色线样本**（表示"按日分色"）：先铺一条完整白描边，再用 `stroke-linecap="butt"` 左右各压一段芯色，
   接缝无缝。

### 分组，别堆成一长条

```
线路        ← D1/D2 分色线、起点 S、终点 E
点位        ← 最高峰、沿途高点、寺院、补给/取水、宿营、高危
地形底图    ← 计曲线、首曲线、步道、公路、溪流、林地
```

用两列网格让**所有样本左边缘严格对齐**，组标题跨两列并带一条渐隐横线：

```css
.lg{display:grid;grid-template-columns:36px 1fr;align-items:center;gap:8px;...}
.lg .grp{grid-column:1/-1;display:flex;align-items:center;gap:7px;...}
.lg .grp:after{content:"";flex:1;height:1px;background:#EDE6DC}
```

### 每个条目写"是什么 + 用在哪"，不是只写名词

- ✅ `最高峰　十王峰 · 1345 m`（读者知道这个符号在本图上只对应哪座山）
- ❌ `山峰`（图上有 30 多个山峰名，说了等于没说）
- ✅ `补给 / 取水　沙弥庵活水 · 药师殿`
- ✅ `计曲线 100 m　粗棕，线上直接标高程数字`（顺便教会读者怎么读这张图）

## 4. 版式连带问题：右栏一长，地图下面就空

**症状**：地图是竖长条（宽高比常 1:2.5）。右栏加了完整图例后，右栏总高**超过**地图列高度 →
`.mapwrap` 的 grid 行高 = 右栏高度，而地图受 `aspect-ratio` 锁定不会拉伸 →
**地图下方留一大块空白**。

**别用 `flex:1 1 auto` 去撑最后一个卡片** —— 那会把空白转成卡片内部的空洞，更难看。

**正解：把最"脚注"的那块搬出右栏，改成地图区之下的通栏面板。**

```html
</aside></div></section>

<section class="panel">
  <div class="ph"><h2>底图与轨迹来源</h2><span class="tagn">全部本地生成 · 不依赖任何在线瓦片服务</span></div>
  <div class="src">                       <!-- grid-template-columns:repeat(3,1fr) -->
    <div><h4>① 地形</h4><p>…</p></div>
    <div><h4>② 矢量</h4><p>…</p></div>
    <div><h4>③ 轨迹</h4><p>…</p></div>
  </div>
</section>
```

来源说明本来就**不依赖窄栏**（三列反而更好读）。搬走之后本轮长图总高 7689 → 7495 px，
地图与右栏底边严格对齐。同时把 `.rail` 的 `justify-content` 设为 `space-between`，
让右栏剩余的卡片在有余量时**均分间距**，而不是让最后一张卡片内部空一块。

## 6. 底图本身怎么"好看"：五个可复现的处方

§1–§3 解决的是"**读得出来**"；这一节解决"**看起来舒服**"。两者会互相牵制
（比如把地形提亮就更容易显脏），所以下面每条都写清"症状 → 根因 → 处方"。

### 处方一：分层设色必须按**本图的实际高程跨度**定制

**症状**：整张图发闷、发脏，像旧报纸；中低海拔全是灰绿＋橄榄卡其。

**根因**：色带照搬了通用的 0–3000 m 版。本图实际只有 **13–1324 m、p50 = 524 m** ——
全图只用到色带的"灰绿 → 卡其"前两档，高处的暖色档**从来没被用到**，
而用到的两档饱和度都极低。

**处方**：
1. 先量高程分布（`np.percentile` + 各高程带面积占比），再定停止点；
2. 把整条"绿 → 暖"的转折**压在 0–1000 m 之内**（覆盖 75% 陆地面积）；
3. 1100 m 以上再收一档陶土色，给主脊一个真正能"跳出来"的暖色顶；
4. 暖色端刻意**离开"纯橙"**（走 米黄 → 杏 → 陶土 → 玫瑰棕），
   免得中层地形和公路/轨迹撞色。

```python
# 九华山（13–1324 m）实测可用的色带
_HYPSO = [(0,    (176, 212, 172)),   # 浅青绿   河谷 / 平原
          (250,  (203, 226, 174)),   # 黄绿
          (500,  (228, 231, 172)),   # 嫩黄绿   （p50 落在此档）
          (700,  (236, 216, 161)),   # 米黄
          (900,  (236, 203, 160)),   # 奶油杏
          (1050, (234, 194, 155)),   # 浅杏
          (1200, (226, 180, 151)),   # 浅陶土
          (1400, (212, 164, 146)),   # 陶土     山顶
          (2000, (186, 146, 138)),   # 玫瑰棕   （本图用不到，留作通用）
          (3000, (162, 128, 126))]
```

### 处方二：抬环境光、收方向光 —— 阴影只比平地暗约三成

**症状**：背光坡一片脏棕灰，整张图发闷。

**根因**：`AMBIENT=0.62 / DIRECTIONAL=0.45` → 背光面只剩 **0.62×**，
把本就偏灰的设色进一步压成"黑泥"。方向和明暗都没错，就是**压得太狠**。

**处方**：`AMBIENT=0.70 / DIRECTIONAL=0.38` → 背光 ≈0.70×、平地 ≈0.97×、迎光 ≈1.08×。
再补一条**高光软限幅**（超出 240 的部分只保留 35%），免得浅色档在迎光坡被 clip 成死白平面。

```python
img = rgb * (AMBIENT + DIRECTIONAL * hs)[..., None]
over = img > 240.0
img[over] = 240.0 + (img[over] - 240.0) * 0.35      # 高光软限幅，亮而不白
```

### 处方三：等高线要"提亮 + 收细 + 半透明融合"

**症状**：计曲线又粗又深，像一条条棕色蚯蚓 —— 整张图最重的"旧地图"信号。

**根因**：两个错误叠在一起。① 线宽 `dilate 2` = 5 px@3008；②
`rgb[mask] = (126,100,72)` 是**硬像素覆盖**，在 1 px 上留下高反差硬边。

**处方**：
- `CONTOUR_DILATE = (0, 1)`（计曲线 3 px@3008 ≈ 1.5 逻辑 px）；
- 颜色整体提亮成**暖灰棕**：首 `(172,155,136)`、计 `(139,111,84)`；
- 改用 **alpha 融合**写回底图，线才像"印在纸上"而不是"贴上去"：

```python
f = rgb.astype(np.float32)
for mask, col, a in ((m_minor, C_MINOR, 0.55), (m_major, C_MAJOR, 0.86)):
    f[mask] = f[mask] * (1 - a) + np.asarray(col, np.float32) * a
np.copyto(rgb, np.clip(f, 0, 255).astype(np.uint8))   # 注意 rgb 是 uint8，必须过 float
```

> 计曲线是首曲线的子集（100 = 5×20），直接"后画覆盖"即可，不必做掩膜互斥。

### 处方四：林地用"乘法染色"，不要用"平铺色罩"

**症状**：地形上出现一块块**多边形硬边**的绿斑，下面的山形被整块抹平。

**根因**：`d.polygon(pts, fill=(198,220,190,95))` 刷的是一块**恒定颜色** ——
既留下硬边，又把晕渲明暗整体拉平。本图 OSM 只有 **2 个** wood 面且面积巨大，
一硬就特别扎眼。

**处方**：画进独立掩膜（`Image.new("L")`），**大半径羽化**，再对底图做乘法着色：

```python
mm = mask.filter(ImageFilter.GaussianBlur(10.0 * S))     # 羽化要大：粗边界必须化成渐变
a  = np.asarray(mm, np.float32)[..., None] / 255.0
base *= 1.0 - 0.09 * a + np.array([0.0, 0.035, -0.022]) * a   # 压深 + 转青绿，明暗保留
```

三条要点：
1. **必须在合成矢量层之前做** —— 否则连道路一起染色；
2. **程度要轻**：OSM wood 面是粗略勾的大块区域，边界本身不精确，
   一旦"看得见"就是错的。目标是"看得出植被更绿更沉"，而不是"看得见一条边界线"；
3. **图例要能表达这一步**：孤立色块说不清"染色"，做个**上=地形底色 / 下=染色后**
   的两段样本（`_woodsw()`）。

### 处方五：缓坡的"起云"和细条纹，靠**真实坡度加权** + 柔化明暗

**症状**：河谷平原上成片灰绿"云斑"；缓坡上有细密的横向条纹。

**根因**：垂直夸张（`z_factor=1.4`）会把 30 m DEM 的微起伏一起放大。
注意——**这不是噪声，是真实微地形**（实测横纵向高频能量只差 1.5 倍），
所以不能简单"多模糊一点"，那会把山脊一起磨掉。

**处方**：
- **按真实坡度加权**（用未夸张的 `arctan(tan_slope)`，阈值才是物理真值）：
  坡度 ≥2.5° 处明暗 100% 保留，<2.5° 渐回平地基准 `sin(alt)`；
- 明暗值再做一个 **≈3 DEM 像素**的柔化（`HS_SMOOTH`）。
  PIL 的 `GaussianBlur` **不支持 `"F"` 模式**（抛 `image has wrong mode`），
  用"降采样 → `Image.BOX` → 升采样"实现等效盒式模糊，O(n) 毫秒级。

```python
w  = np.clip(np.arctan(tan_slope) / math.radians(2.5), 0.0, 1.0)
hs = hs * w + math.sin(math.radians(ALT)) * (1.0 - w)

im = Image.fromarray(hs.astype(np.float32), "F")
hs = np.asarray(im.resize((im.width // 3, im.height // 3), Image.BOX)
                  .resize(im.size, Image.BICUBIC), np.float32)
```

> 柔化明暗还带来一个额外好处：**明暗柔和 + 线划锐利** ——
> 这正是纸质地形图的经典质感（晕渲是背景，等高线/注记是前景，两者不该抢锐度）。
> 配套把 USM 从 `(3,55,4)` 收到 `(3,45,3)`，否则提亮后的底图会满屏"砂砾感"。

### 改动清单（第二轮）

## 8. 交付前的第二次自检：可读性、字号、手机端

> ⚠ **§8.2 的"出第二版手机长图"已废弃**（本技能不再生成手机版长图）。
> 但 §8.1 的对比度自检、以及 §8.2 里"无头浏览器最小窗宽"那条**探针经验仍然有效** ——
> 现在它只用于 `qa_guide.py` 的 phone 断点探针（`--window-size=600,…`，绕开最小宽钳制）。
> 宽屏长图的裁剪现在由 `shoot_guide.py` 用「先量版式、再截一次」完成。

第一轮把"颜色对不对"解决了，第二轮要解决的是"**在读者真正看这张图的那一档尺寸下，读不读得出来**"。
下面五条都是量出来的，不是审美判断。

### 8.1 先量对比度：四档灰看着"精致"，实测全在 2.2–3.1:1

原设计的灰阶是 `#8C93A0 / #939AA6 / #9AA1AC / #A6ADB8` 四档，看着层次细腻。
用 WCAG 公式一算：

| 用途 | 原色 | 在白底 | 在米底 |
|---|---|---|---|
| 备注 / 页脚 / 面板副标 | `#8C93A0` | 3.09 | **2.92** |
| 图例说明文字 | `#939AA6` | 2.90 | **2.72** |
| 表头 | `#9AA1AC` | 2.66 | **2.50** |
| 图例分组标题 | `#A6ADB8` | 2.30 | **2.17** |

**全部低于 AA 的 4.5:1，而这恰好是页面上字号最小的那批字（10.3–12.8 px）。**

正解不是"每一档都调深一点"（四档会挤成一档，层次反而没了），而是**换通道做层次**：

```
#1F2430  14.7  标题
#2A3140  12.3  图例条目名
#3A4250   9.6  正文
#4A5261   7.4  说明
#5A6270   5.8  次级
#5F6875   5.3  数字下的标签 / 面板副标
#68717E   4.66 ← 唯一一档"最浅可用"，所有小字统一用它
```

对比度只管"看得见"，层次交给**字重（400/600/700/800）与字号**去表达 —— 这是更干净的做法。
唯一豁免：纯装饰性分隔符（`|`、`›`）可保持很浅，WCAG 对 incidental 内容不计入。
**自检脚本**：正则扫 CSS 里所有 `color:#RRGGBB`，对最差背景算比值，`< 4.5` 的报警。

### 8.2 长图在手机上按满宽显示 = 再好的版面也读不了

这是一条容易被忽略的**量化**事实：

```
宽屏长图 2344 px 宽（1120 CSS 版心 × 2 倍像素密度）
手机屏幕 390 px 宽  →  缩放比 0.166
12.8 px 的正文  →  屏幕上 2.1 px
```

整块右栏（时间表 / 图例 / 分段速查）在手机上就是一片灰噪。
**"把字号加大"救不了**：要 readable 就得让**版心设计宽度本身**接近手机宽度。

正解：**同一份 HTML 出两个尺寸**，加一段单栏响应式，再用不同的窗宽各截一张。

```css
@media (max-width:900px){
  .page{width:100%;max-width:430px;padding:16px 15px 24px}
  .mapwrap{grid-template-columns:1fr}      /* 右栏自然落到地图下方 */
  .rail{height:auto;justify-content:flex-start}
  .stats{grid-template-columns:1fr 1fr}    /* 4 项改 2×2 */
  .days,.ngrid,.src{grid-template-columns:1fr}
  /* 右栏字号整体给到 13.4–14.2 px */
}
```

三个关键点：

1. **DOM 顺序天生就支持**：`.mapwrap` 里本来就是 `地图 → 右栏`，改成单列后右栏自然下移，
   HTML 一行都不用动（当初把「来源」搬出右栏也帮了忙）。
2. `<meta name="viewport">` 从 `width=1120` 改成 `width=device-width,initial-scale=1` ——
   **原来 HTML 在手机上也是糊的**，`width=1120` 会把整页缩到手机宽度。
3. 渲染：同一个 HTML，宽窗出宽屏版、**更宽的窗**出手机版（见下条：不要按窗宽算裁剪）。
   430 CSS × 2 = **860 px 成品**，满宽下正文约 13 个屏幕像素，不用放大就能读。
4. 手机版总高会更长（本例 860×13137 ≈ 1:15），但按满宽折算是 **6–7 屏**，属于正常长图。

#### ⚠ 最容易静默翻车的一步：无头 Chrome 有**最小窗口宽度**，不要用窗宽反推裁剪区间

真实返工：`--window-size=430,7200` 的截图是 860 px 宽没错，但**版面不是按 430 排的**。
注入脚本一量就现形：

```
--window-size=430  →  clientWidth = 500          ← 被钳制到最小值
page L=35.0 R=465.0 W=430.0                      ← .page 居中在 500 里
canvas 430  →  实画区只有 x 0…430，右侧 35 px 整条丢掉
```

后果不是"图小了 35 px"这么轻：`.page` 内的文字仍然按 430 版心断行，
但我们只截了它左边 430−35 = 395 px —— **每一行文字的末尾都缺几个字**。
又因为 `body` 与 `.page` 底色相同（#FBF8F4），肉眼看不出是被裁，
第一反应会误判成"换行不对/字号太大"。

修法：**按像素量版心边界，别猜窗口尺寸**。

```python
# 1) 渲一份临时 HTML：给 <body> 注入一个与版心明显不同的底色（只用于量边界）
src = HTML.read_text(encoding="utf-8").replace("<body>", '<body style="background:#DED8CE">', 1)
# 2) 截图后量：整条落在版心内的列/行，其像素必然大量偏离探针底色
off  = np.abs(a - a[2, 2]).sum(axis=2) > 14
cols = np.where(off.sum(axis=0) > 0.5 * H)[0]       # 版心左右边
rows = np.where(off.sum(axis=1) > 0.5 * W)[0]       # 版心上下边
# 3) 手机版裁到版心（全出血）；宽屏版保留版心外的纸面外框
# 4) 断言 x1-x0 == 设计宽 × SCALE，不等就报警 —— 缺字这类事故必须响，不能静默交付
```

**自检**：出图后扫一遍左右边缘两列有没有深色像素（`a[:,W-3:W-1].min() < 120`）。
有就是被裁了。本例修前右边缘 46 行有字、修后 0 行。

### 8.3 SVG 图内文字会跟着版心一起缩，必须重出一份

地图与剖面都是**固定 viewBox 缩放到容器宽度**的。版心从 1032 → 400 CSS，
图内 11.8 px 的坐标轴数字变成 `11.8 × 0.39 ≈ 4.6 px`。所以：

- 给生成函数加一个 **`fs` 字号倍率**参数（`profile_svg(fs=2.4, ...)`）。
- 倍率怎么定：**先算缩放比，再反推**。剖面 viewBox 宽 1000，手机版心
  `430 − 版心内边距 30 − 面板内边距 30 = 370` CSS → 缩放比 0.37。
  要拿到 10.5 CSS px 的轴数字：`11.8 × fs × 0.37 = 10.5` → **fs ≈ 2.4**。
  （第一版凭感觉写 1.7，实到 7.4 CSS px，在手机屏上只有 6.7 像素 —— 等于没修。）
- 同一份 HTML 里放两份 SVG，用 CSS 断点二选一：`.prof-d{display:block} .prof-p{display:none}`，
  媒体查询里对调。桌面版一个字都不变。
- **字号放大后放不下的标注必须主动删**：剖面 9 个沿途高点标注在 2.4× 下单个约占 1/4 图宽，
  必然互压 —— 手机版只留 `D1/D2` 与 `起点/打鼓岭/终点`，高程交给「关键点时间表」与逐日卡，
  信息不丢，图还干净。
- 但**地图的图内注记不要跟着放大**：地图是给人"双指放大看细节"的 artifacts，
  注记放大只会互相压，反而更难读。窄版应该在图下写一句
  「地图细节建议放大；另附《全线地图》高清图」，把"看细节"这件事交给专门的产物。
- 放大字号时**左轴要一起右移**（`pl` 参数）：`1400` 这种四位标签在大字号下会往左长出画布被裁掉。
  定 `pl` 的算法：`pl ≥ 数字宽度(4×0.55×11.8×fs) + 间隔 + 竖排轴标题的列宽 + 间隔`。
  竖排的「海拔 (m)」也要从 `x=18*fs` 收到 `x=12*fs`，否则它会和刻度数字撞在一起。
- **端点标签会撞上最右/最左的刻度数字**（桌面版也有，属于长期潜伏的缺陷）：
  终点标签锚在右端、`30` 刻度也在右端，两者原本只差 4–7 px，读出来是「…25430」。
  修法：刻度行归一档（`pb + 18*fs`），**起点/终点提到下一行**（`pb + 36*fs`，
  start 锚 `pl+9*fs`、end 锚 `pr-9*fs`、中间的「打鼓岭」仍紧跟其点位），
  x 轴标题「累计里程 (km)」放进这同一行的中缝（原来在 `ph-7*fs`，
  正好压在终点标签旁边）。改完先按字号估一遍三者的宽度，确认互不相交。

### 8.3.1 窄版是另一套排版：孤字、悬空分隔符、卡片不等高

版心从 1032 掉到 400 之后，"能用"不等于"好看"。四类反复出现的问题，全都是**量出来的**：

| 现象 | 成因 | 做法 |
|---|---|---|
| 卡片文案末字独占一行（`…（九华山最高\n峰）`） | 卡片内宽 ≈167 px ≈ 13 个汉字，文案 16 字 | 窄版换**短标签**（`.donly` / `.monly` 两份文案 + 断点切换），四张卡恢复单行等高 |
| 行末悬空一个 `\|` | 分隔符是独立的 flex 子项，后面的项换行后它留在上一行末尾 | 窄版直接 `display:none` 掉那一个分隔符（`.dsep2`），并把要换行的项设 `flex:0 0 100%` 主动换行 |
| 句中被拆成 `18.5–` / `20 km` | `–` 之后是合法断行点 | 生成时用正则把「数字＋单位」包成 `<span class="nb">`（`white-space:nowrap`），注意只认**有空格**的写法，别把 `559m` 改成 `559 m` |
| 副标题折成行末一个孤零零的 `\|` | 桌面用 `\|` 分隔三句，窄版仍按同一句流排 | 窄版换成**三整句**：`<br class="brm">`（桌面 `display:none`）+ 分隔符也分桌面/窄版两份（`.ds` / `.ms`） |

要点：这些都是**用同一份 HTML 做响应式**的代价，别去改桌面版文案；
两份文案 + 断点切换，桌面一个字都不动。

### 8.5 图例样本：统一底板，且底板不能是纯白

## 9. 地图标注定位：写自动避让，不要手工逐个调 dx/dy

真实返工过两轮（南天山北线），两轮的根因完全不同，**必须一起修**，否则程序会告诉你"没问题"而图上仍然糊。

### 9.1 第一轮：锚点方向选错 → 文字直接出画布

给西侧点位配 `anc=end`（文字向左展开）时，远点位的 `text_x` 会变成 `x - 30` 这类负向坐标。
本线 5 个标注落到 **text_x = 63–180**，图幅宽 1504，**整条文字被推到画布外**。

- **规则**：文字要往**画布内侧**展开。西侧点一律 `anc=start`（dx > 0 向右摆），东侧点 `anc=end`。
- 只有轨迹整体偏东/偏西时才需要手工反着摆，属于个案。

### 9.2 第二轮：程序判定"不重叠"，实际渲染糊成一团（两个根因）

**根因 A：字宽估算偏小。** SVG 文字带 `stroke-width` 的白色描边 halo（`7*PS ≈ 6 px`），
实际占位比字面宽约 **12 px**。系数估小 → 碰撞检测全部放行。

- 汉字按 `1.0` 字宽、西文/数字按 `0.62`（别用 0.58）；
- 末尾再留 `+88` 余量给海拔后缀（` 4083 m`）与 halo；
- 宁可估大一点，估大的代价只是多错开一行。

**根因 B（更隐蔽）：只查了"文字 vs 文字"，没查"文字 vs 别的点的符号"。**
本线「冰湖」（80.538853, 42.373335）与「艾勒门特达坂」（80.551369, 42.376950）**经度只差 0.013°（≈1 km）**，
像素上几乎重合 —— 冰湖的文字左端直接把对方的蓝雪花图标盖掉了。只查文字框永远查不出来。

- **修法**：渲染前先把**全部点位的符号**登记为占位区（半径 `_PIN_R = 24`），再逐个摆文字。
- 顺带：两点像素距离近到一定程度时，让它们**分居线的两侧**（一个 `dx>0` 一个 `dx<0`），
  比在同一侧硬错开更易读。

### 9.3 落地实现（`map_svg._layout()`）

```python
_OCC = []          # 已占位矩形，后画的让开先画的
_PAD = 22          # 画布内边距（避开指北针/比例尺白底）
_PIN_R = 24        # 点位符号半径（含白圈）

def _layout(x, y, dx, dy, anc, w, fs):
    h = fs * 1.6                                   # 行高，取 1.6 而非 1.2：描边 halo 会吃掉间距
    cand_offsets = [0, -h, h, -2*h, 2*h, -3*h, 3*h, -4*h, 4*h, -5*h, 5*h, -6*h, 6*h]
    # 横向候选：(偏移, anchor)。第一组＝给定方向，第二组＝翻到线的另一侧
    if anc == "middle":  hplans = [(0, "middle")]
    elif dx >= 0:        hplans = [(dx, "start"), (-abs(dx), "end")]
    else:                hplans = [(dx, "end"),   (abs(dx), "start")]
    for hdx, hanc in hplans:
        for ody in cand_offsets:
            tx, ty = x + hdx, y + dy + ody
            x0, x1 = ((tx, tx+w) if hanc == "start" else
                      (tx-w, tx) if hanc == "end" else (tx-w/2, tx+w/2))
            y0, y1 = ty - h/2, ty + h/2
            if x0 < _PAD or x1 > IW-_PAD or y0 < _PAD or y1 > IH-_PAD:
                continue                                   # 越界
            if any(x1 > a and x0 < b and y1 > c and y0 < d for a, c, b, d in _OCC):
                continue                                   # 撞已占位
            _OCC.append((x0, y0, x1, y1))
            return round(tx, 1), round(ty, 1), hanc
    # 兜底：全部候选都冲突 → 用最初候选并强制钳进画布
    ...
```

调用方（`build_overlay`）只要保证两件事：


具体落点交给 `_layout()`，**改点位时不用再逐个试坐标**。

### 9.4 比例尺要放在轨迹的"空白扇区"，不是固定角

比例尺习惯放左下角，但**轨迹的重心未必在中部**。本线东半部（50–111 km）横向铺开，
西侧 40–50 km 冰川段全挤在 `x < 430` 的窄带里 → 左下角正是最密的标注区，比例尺白底直接压住 5 个地名。
改放**右下角**（本线右下大片留白）立刻干净。

- 摆之前先看轨迹的分布重心（`x` 的直方图），挑**点位最稀疏的角**；
- 别用"缩到很小"来回避遮挡 —— 缩小后读不出比例感，等于没放。

### 9.5 自检（不要靠肉眼在整图上找）

1. 量每个标注的 `text_x/text_y` 与文字框，**断言全部落在 `[_PAD, IW-_PAD] × [_PAD, IH-_PAD]` 内**；
2. 两两求矩形相交，**断言 0 对重叠**（20 个 POI 是 190 对，跑起来是毫秒级）；
3. **渲染后放大截图复核** —— 程序只能查"框重叠"，查不出"字宽估算偏小导致的视觉糊"。
   本线把 40–60 km 密集段裁出来放大 2× 才看出「冰湖」压住了「艾勒门特」的图标。
4. 锚点方向修完后，**左侧出界数应为 0**（修前 5 个）。
