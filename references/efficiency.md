# 效能复盘：一份攻略为什么会做 45 分钟，怎么压到 15 分钟

来源：党岭三湖连穿 3 天顺穿（两步路 KML → 5 件产物）全程实测 wall clock ≈ 45 min。
本文只讲**时间与返工**，具体技术坑见各自的 `pitfalls-*.md`。

---

## 1. 先破除一个错觉：慢的不是计算，是「改一点 → 重跑 → 再看」

实测单步耗时（本机，Windows / Edge）：

| 步骤 | 单次耗时 | 本轮跑了几遍 |
|---|---|---|
| DEM 瓦片下载（143 片，z15） | **~8 min（首次，一次性）** | 1 |
| `make_terrain.py`（晕渲 + 等高线 + USM） | **~2 min** | **4–5** |
| `fetch_osm.py` | ~10 s | 1 |
| `build_<线路>.py`（出 HTML） | **< 1 s** | 10+ |
| `shoot_<线路>.py`（一张长图） | **7 s** | 4 |
| `render_map_hi.py`（3008 px 地图） | **5 s** | 4 |
| `make_gpx.py` | < 1 s | 2 |

**结论：除了 DEM 下载和 `make_terrain`，下游全部是秒级。**
所以"重跑一次"几乎不花钱 —— 真正烧掉 45 分钟的是：

- **返工轮次**（本次 18 项，见 §2）；
- **每一轮的判断成本**：尤其"我看不到图"时，只能临时写探针脚本去量，一轮就是好几分钟。

优化重心因此是 **① 减少返工轮次 ② 把"看效果"自动化**，而不是去加速脚本。

## 2. 本次 18 项返工，按可预防程度分类

### A 类 · 环境/低级错误（5 项）—— 开局 30 秒预检就能全部消灭

1. 自带 Python 无 numpy/Pillow → 中途 `ModuleNotFoundError`，切系统 Python 重来；
2. 没装 Chrome，只有 Edge → 渲染脚本硬编码路径要改；
3. `out/` 与 `scripts/out/` 两套路径约定不一致 → 文件找不到；
4. `P()` 被传成元组 `P((lon,lat))` → `TypeError`；
5. 用 sed 式替换改 bbox，把换行吃掉 → `SyntaxError`。

**共性：都不是"做错了设计"，是"环境约定没先确认"。** 见 §3.1。

### B 类 · 视觉问题（9 项）—— 本次最贵，因为看不见图只能靠猜

6. DEM 空洞 → 高程 `−5362 m`（**改了两轮**：全局中位数法不行，才换局部参考面法）；
7. 地图宽高比 1504×1197 太瘦高 → 改 bbox 纬度；
8. 步道紫撞主线 D3 紫 → 改中性灰；
9. 公路橙撞主线 D1 橙红 → 改暖砂色；
10. 步道芯改暗后，纸白 casing 反成全图最亮（"白鬼线"）→ 去 casing；
11. 图例被摆到地图中间 → 落点限制到四角/边中点；
12. 图例与比例尺都选了左上角，叠在一起 → 加 `used=` 参数；
13. 搭车点用了水滴图标（读成水源）→ 新增「车」图标；
14. 标签宽度高估 `+88` → `+34`，导致标签蹭到点位并跳行。

**共性：8/9/10/11/12 全是"配色与布局"，本可以在动手前一次性定完。**
改色 3 轮 = 3 × (2 min 底图 + 15 s 下游 + 我判断) ≈ 8 min 白烧。见 §3.4 / §3.5。

### C 类 · 手机端（3 项）—— 桌面版没定稿就兼顾手机，来回改

15. 长图 `_page_box` 阈值写错 → 手机版直接崩（详见 `pitfalls-layout.md` §9）；
16. 手机地图字号只有 5.4 CSS px → 另出手机版地图（详见 `pitfalls-map-svg.md` §3）；
17. 标注被避让算法甩到 285 unit → **改了两轮**（先补横向兜底没生效，才发现是"先定方案再上下试"的结构问题）。

### D 类 · 导出（1 项）

18. GPX 段界点写了两遍（2870 ≠ 2868）→ 改半开区间。

## 3. 七条可复用做法

### 3.1 开局先跑 `preflight`：把 A 类错误压缩到 30 秒

任务一开始，先用一个脚本把环境全断言一遍，**不要等它中途崩**：

```python
# scripts/preflight.py —— 30 秒内跑完，任何一条不过就立刻修
import importlib, shutil, sys
from pathlib import Path
for m in ("numpy", "PIL"):
    importlib.import_module(m)          # 缺就直接 ModuleNotFoundError，别等跑到第 5 步
BROWSER = next((p for p in (
    r"C:\Program Files\Google\Chrome\Application\chrome.exe",
    r"C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe",
) if Path(p).exists()), None)
assert BROWSER, "没找到浏览器"          # ⚠ 别假设一定有 Chrome
assert (HERE / "out").is_dir()          # 路径约定：所有脚本统一用 HERE/"out"
```

顺带把 KML 格式探测也放进来（`<gx:coord>` 数 vs `<LineString>` 数），
**先判断格式再选解析脚本**，否则会得到 0 个点 —— 见 `track-prep.md` §2.1。

### 3.2 写 `make_all.py` 一键编排，别手敲 4–5 条命令

每次改参数都要手敲 `make_terrain → build → shoot desk → shoot phone → render_hi`，
命令本身不慢，**慢在人的往返**。一条命令跑完，改起来才敢改：

```python
# scripts/make_all.py  —— 支持跳步：python make_all.py --skip-dem
STEPS = [("地形", "make_terrain.py"), ("HTML", "build_dangling.py"),
         ("长图", "shoot_dangling.py desk phone"), ("地图", "render_dangling_map_hi.py"),
         ("GPX", "make_gpx.py"), ("自检", "qa_long.py")]
```

**关键：必须支持 `--skip-dem`。** 改配色/改标注根本不用动 DEM，
加了跳步后单轮从 2 min 降到 ~15 s，改起来心理成本骤降。

### 3.3 数据先冻结，再动底图（省掉"边查边改"）

`route_def.py`（地名 / 海拔 / 分日断点 / 图标 / 里程）在**跑 `make_terrain` 之前必须定稿**。
本次是边查资料边改，导致底图渲染完了数据还在动。

定稿判据（都满足了再往下走）：
- 分日断点有依据（时间戳自然断点或资料双证），不是"看着差不多"；
- 每个地名的海拔有出处（轨迹实测值 / OSM / 资料），三者冲突时写明取哪个；
- `POIS` 的 `kind` 与图标一一对应（别出现"搭车点用水滴"）。

### 3.4 配色一次定完，不要"改一个跑一轮"

主线四色确定后，**按色相分配表一次性把底图所有元素定死**，再进 `make_terrain`：

| 底图元素 | 色相 | 备注 |
|---|---|---|
| 等高线 | 棕 | 首/计曲线靠明度分 |
| 水系 | 蓝 | |
| 公路 | **暖砂**（芯 240,208,172 / 边 200,170,144） | 不能是橙，会撞 D1 |
| 步道 / 小径 | **中性灰 (140,138,134)** | 不能带色相，否则迟早撞某一天的主线 |
| 主线路 | D1 橙红 / D2 绿 / D3 紫 / D4 蓝 | |

配套三条硬规则（都是本次踩出来的）：
- **底图元素一律不带色相**，靠明度 + 线宽 + 虚线节拍区分；
- **芯色改暗后必须同步去掉浅色 casing**，否则 casing 变全图最亮；
- 图例样本与底图**共用同一组常量**，改色不会指向旧色。

### 3.5 底图先用「快出模式」定参数，再跑全量

`make_terrain` 2 min 一次，改配色要试好几轮。加一个 `--fast`：
降采样（如 1/4）+ 跳过等高线绘制 + 跳过 USM，几秒出一张能看配色和构图的样图。
**定完配色/宽高比再跑全量**，能省下 2–3 轮 × 2 min。

### 3.6 ⚠ 看不到图时，**禁止产出"检查图"**，全部改成数值断言

本次最大的浪费：产了 11 张 `_chk_*` / `_qa_*` 检查图，但读不了图 ——
这些图**只起到了做数值统计的作用**，出图本身（每张 5–15 s）和来回切换全是白费。

正确做法：直接写断言脚本，把"看"变成"量"。本次有效的四类断言：

```python
# ① 切边：最外 2 px 的深色占比应 ≈ 0
frac = (lum[:, :2] < 120).mean()
# ② 标注：越界 / 两两重叠 / 落进图例的轨迹点数
# ③ 版式（注入 JS，用 --dump-dom 取回，见 pitfalls-layout.md §9）：
#    横向溢出、越出版心的元素、被裁的元素、最小字号
# ④ 手机地图实际字号：SVG unit × (版心内地图宽 / viewBox 宽)
```

**并且自检脚本要在第一次 build 后就跑，不是留到最后。**
本次 `qa_long.py` 是最后才写的，前面十几轮全靠临时脚本，等于每轮重复造轮子。

### 3.7 并行：能省多少，实测过（别抱幻想，也别不做）

`make_all.py` 已按 **DAG 分层并行**（`osm → dem → html → {long, map} → qa`，`gpx` 无依赖挂 wave0）。
同一层内 `subprocess` 并发，输出各写临时文件（共享 pipe 会被缓冲区打满互相卡死）。

```
wave0:  osm ∥ gpx
wave1:  dem              ← 独苗，8 min，并行救不了
wave2:  html
wave3:  long ∥ map       ← 加 --split 后是 long(desk) ∥ long(phone) ∥ map
wave4:  qa
```

```bash
python scripts/make_all.py --split long=desk,phone   # 长图两版拆成两个进程
python scripts/make_all.py --serial                  # 排错时关掉并行
python scripts/make_all.py --dry-run                 # 先看分层认没认对脚本
```

**党岭实测（同一台机器、同一份 HTML）**：

| | 串行 | 并行 | 省 |
|---|---|---|---|
| long(desk+phone) + map | **17.2 s** | **8.4 s** | 8.8 s（51%） |
| 其中 desk / phone / map 各自 | 7.9 / 3.8 / 5.5 s | 并行后整层 8.4 s | |

**但把它放回 45 min 里看，只占 3%。** 原因很简单：

- **DEM 下载 8 min 在 wave1 是独苗**，它前后都没有能跟它并行的活（osm 是它的前置，
  10 s 而已）。把 10 s 的 OSM 塞进并行，最多省 10 s —— 典型的 Amdahl。
- 真要压这 8 min，得动 `make_terrain.load_dem(workers=10)`：提到 16–24、
  并把失败退避 `sleep(0.5*(a+1))` 压短（失败多时这条会明显拖慢）。**这是唯一分钟级的并行收益。**
- 剩下的下游全是秒级，**并行在这里买的是"人不用守着"，不是算力**。

所以并行的正确姿势：**默认开着，但别为它花时间调参**。省时间的排序永远是：
① 减少返工轮次 ≫ ② DEM workers 与 `--fast` ≫ ③ 分层并行 ≫ ④ 优化单脚本。

⚠ **`--split` 的两个坑**：
- 参数解析是「逗号=同组多参数、分号=多组」。写成 `long=desk,phone` 才是拆两版；
  曾用 `|` 分隔，在 shell 里直接变管道符，结果 phone 那一版被静默漏跑（图没更新但脚本报 ✓）。
- 只拆**产物互不重名**的步骤（desk/phone 的 raw 与 probe 文件名都带 mode，安全）。
  脚本不认这个参数时，多余 argv 会被静默忽略。

**agent 侧的并行才是大头**：阶段 1 数据核定时，「网络检索（8264 行程表 / 两步路游记 /
约伴帖）」与「本地轨迹拐点分析」互不依赖，可以**同一次回复里并发发多个搜索、或派子 agent 并行跑**，
这是 5–10 min 级别，比脚本并行（秒级）高一个量级。

## 4. 建议的任务节奏（带 gate，不要跳）

| 阶段 | 做什么 | 通过 gate 才能往下 |
|---|---|---|
| 0 | `preflight` + `make_all` 起链（wave0 自动 `osm ∥ gpx`）；**资料检索与轨迹拐点分析并行派** | 环境全绿、KML 格式判断正确、里程与作者口述对得上 |
| 1 | 冻结 `route_def.py`（地名/海拔/分日/图标） | 每个海拔都有出处，冲突已写明取舍 |
| 2 | 底图：`--fast` 定配色与宽高比 → 全量 | 高程 min/max 落在该地区已知区间；宽高比合适 |
| 3 | HTML 桌面版（地图 + 剖面 + 卡 + 表） | 自检：标注越界 0 / 重叠 0 / 落入图例 0；版式审计无溢出 |
| 4 | **手机版**（另出地图 + 剖面 + 长图） | 手机地图字号 ≥ 10 CSS px；长图宽 == 430×2 |
| 5 | 导出：`make_all --split long=desk,phone`（长图两版 ∥ 高清地图，8.4 s） | 切边扫描 0；GPX 回读校验 trkpt 数 == 原始点数 |
| 6 | 回写本技能 | 新坑已进对应 `pitfalls-*.md` |

**不要在阶段 3 还没过 gate 时就去碰阶段 4** —— 本次 C 类 3 项返工全是这么来的。

## 5. 一句话总结

> 这份工作的成本**不在算力，在迭代次数**。
> 省钱的三板斧：**预检把低级错误提前、编排脚本把往返成本归零、断言把"看效果"自动化。**
> 剩下唯一必须花时间的是阶段 1 的数据核定 —— 那部分省不得，省了后面全要还。

## 6. 本机环境坑（脚本突然崩先查这三条）

- **系统 Python 3.12 才有 PIL/numpy**：默认 `python` 无 PIL。所有图像脚本用
  `C:/Users/yanp2/AppData/Local/Programs/Python/Python312/python.exe` 绝对路径跑。
- **fetch_tiles_cyc 在 import 时解析 `sys.argv`**：包装脚本（replay_tint 等）要先
  `sys.argv = sys.argv[:1]` 再 import，否则自己的参数被它当成 zoom 吃掉报
  `invalid literal for int()`。
- **build_route().pts 是 (lon,lat) 二元组**，高程在 `r["ele"]`——探针里 `p[2]` 直接
  IndexError。探针脚本落盘复用（probe_dem.py），不要每次 inline 重写。
