# 自渲染地形底图：OSM 数据 + SRTM 高程（不依赖任何瓦片服务）

**为什么要自己渲**：瓦片服务会挂（318318 整站 567）、会收费、会有 key、会被 WAF 拦，且官方 OSM 瓦片站
**明文禁止批量下载**。而一份攻略长图要 ~1300 张 z15 瓦片，属于"批量"。用开放 DEM 自己渲，一次投入，
之后无限次重出、无速率限制、无版权风险。

对应脚本（三个，已全部跑通）：
- `scripts/make_terrain.py` — DEM → 晕渲 + 等高线 + 分层设色（本文件 §1–§5）
- `scripts/fetch_osm.py` — Overpass 抓 OSM 矢量 → `out/osm.json`（§6）
- `scripts/draw_osm.py` — 把 OSM 矢量叠到地形图上（§6）

---

## 0. 先想清楚要哪一种"自己渲染"

| 路线 | 做什么 | 代价 | 什么时候用 |
|---|---|---|---|
| **重型 · 完整 OSM 渲染栈** | PostGIS + osm2pgsql 导入 `china-latest.osm.pbf` → Mapnik + OpenTopoMap 样式 → 起 TileServer GL / renderd | 需要 Docker、几十 GB 磁盘、导入数小时、机器要好 | 要做**全国/大区域**、要任意缩放、要复刻 OpenTopoMap |
| **轻量 · DEM 地形 + OSM 矢量注记** ✅ 推荐 | 开放 DEM → 晕渲 + 等高线 + 分层设色；OSM 只取**路网/地名矢量**叠上去 | Python + numpy/PIL，几分钟出图 | 做**单条线路/单个景区**的静态攻略图（我们的场景） |

**关键判断**：你要的是"一张好看的静态地形底图"，不是"一个瓦片服务"。那就走轻量路线——
不需要 PostGIS、不需要 Mapnik、不需要导入 OSM 全量数据。OSM 那部分只用来**补齐地名和路网**，
用 Overpass 按 bbox 精准取几十 KB 矢量即可。

## 1. DEM 数据源（都免钥匙、免注册）

| 源 | 分辨率 | 形态 | 直链 |
|---|---|---|---|
| **AWS Terrain Tiles (Terrarium)** ✅ 首选 | 混合（含 SRTM 30 m、局部更高） | Web Mercator PNG 瓦片，z≤15 | `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png` |
| AWS Terrain Tiles (Skadi) | SRTM 1″ ≈ 30 m | `.hgt.gz`，1°×1° 分块，**经纬度栅格（非 Mercator）** | `.../skadi/N30/N30E117.hgt.gz` |
| Copernicus DEM GLO-30 | 30 m（更新、质量更好） | GeoTIFF，1°×1° 单文件 ~48 MB | `https://copernicus-dem-30m.s3.amazonaws.com/Copernicus_DSM_COG_10_N30_00_E117_00_DEM/...tif` |
| NASA SRTM GL1 | 30 m | 需 Earthdata 登录 | 不推荐（要账号） |

**首选 Terrarium 的理由（很重要）**：它是 **Web Mercator 网格**，和你原来下载的底图瓦片**同一套像素网格**。
直接拼接裁剪即可，**投影零误差、不需要重投影**。Skadi/Copernicus 是经纬度栅格，用它就得自己做
WGS84→Web Mercator 重采样（`rasterio.warp` 或手写双线性），平白多一层出错面。

### Terrarium 高程解码

```python
a = np.asarray(Image.open(io.BytesIO(png)).convert("RGB"), dtype=np.float32)
elev_m = a[..., 0] * 256.0 + a[..., 1] + a[..., 2] / 256.0 - 32768.0
```

三个通道一起编码，**精度 1/256 m**，不是普通的灰度图。漏掉 `B/256` 会带来最多 1 m 的台阶。

## 2. 坑一：DEM 瓦片的 z 必须等于底图投影的 z

这是最容易翻车的地方。底图投影用的 z 存在 `out/base_meta.json` 的 `z` 字段里，
下游**一律从 meta 读**（`guide_common.projector_of(meta)` / `m_per_px(meta)`）——
B 路线遗留脚本 `build_base_map.py` 曾用模块级 `Z` 硬编码，那是错的做法，别照抄。所以：

> **`make_terrain.py` 的 `DEM_Z` 必须 == 下游所有投影用的 z**，而唯一真相源是 `base_meta.json`。

否则 `base_meta.json` 里的 `tx0/ty0` 属于 z14 网格，而 projector 按 z15 算 —— 轨迹会整体飘走
（差一个 2 倍尺度，肉眼就是"线完全不在山上"）。

terrarium 最高 z15，正好等于我们出图用的 z15，所以取 `DEM_Z = 15`。
若必须用更低级别（省流量），**要么把 build_map 的 Z 一起改，要么在 meta 里带上 z 并让 projector 读 meta["z"]**。
现行实现取后者：`meta["z"]` 是唯一真相源，降档后下游自动跟随，**不会错位**。

### 2.1 ⚠ 长线必须自适应降档（否则内存爆炸、渲一张图 25 分钟）

> **2026-10-10 狼塔 C+V 实测**：窗口 0.75°×0.57°（86°E、43°N，156 km 的 C+V 大线），
> z15 需要 **377 M px**（约 5760 张瓦片）→ 单个 float32 数组 1.4 GB，
> `paint_contours` 还要在上百个高程层上各扫一遍全图 →
> **实测 25 分钟、峰值内存 11.5 GB**（机器差点进 swap），而成品只有 3008 px 宽。
> 这 25 分钟几乎全是"算完就丢"的浪费：DEM 精度远细于画布。

正解：**按窗口像素数自适应降档**（`pick_dem_z()`）：

```python
DEM_MAX_PX = 40_000_000        # 40 M px 上限
# z15 → z14 → z13 …（z 每降 1 级，瓦片数 /4）直到 ≤ 上限
```

- 狼塔 377 M px @z15 → 自动降到 **z13（24 M px，像素少 15 倍）**，渲图从 25 分钟降到 ~1 分钟；
- 质量无损：成品 3008 px 覆盖 96 km，约 **32 m/px**；z13 ≈ **19 m/px**，仍**细于成品**；
  z12 才勉强不够（38 m/px），所以下限设 `z > 12`。
- **降档不会错位**：`meta["z"]` 记实际用的 z，下游 projector 一律读它（§2 的前提已满足）。
- 判据（自检用）：`DEM 分辨率(m/px) < 成品分辨率(m/px)` 即可放心降档。
- 日志会打印 `窗口较大（377 M px @z15 > 上限 40 M px）→ DEM 自动降到 z13（约 24 M px）`，
  看不到这行说明窗口不大、没降档，属正常。

**推论（更普适）**：任何"栅格中间产物"都该按**最终画布**定分辨率，而不是按数据源上限——
数据源能给的精度 ≠ 你需要的精度。

## 3. 晕渲（hillshade）：GDAL Horn 算法

```python
res = 156543.03392 * cos(radians(lat)) / 2**z      # Web Mercator 米/像素（注意随纬度收缩）
# 3×3 Horn 核
dzdx = ((c + 2f + i) - (a + 2d + g)) / (8*res)
dzdy = ((g + 2h + i) - (a + 2b + c)) / (8*res)
slope  = atan(hypot(dzdx, dzdy) * z_factor)
aspect = atan2(dzdy, -dzdx)
hs = sin(alt)*cos(slope) + cos(alt)*sin(slope)*cos(az - aspect)     # 裁到 0..1
```

- 光源惯例：**方位角 315°（西北）、高度角 45°**。这是国际制图惯例，改成正南或正东会立刻"看起来不对"。
- **`res` 必须随纬度变**（`×cos(lat)`）。Web Mercator 在高纬度被拉伸，用常数会算出错误的坡度。
- **`z_factor` 建议 1.2–1.6**：中国东部丘陵起伏小，原始夸张下几乎看不出立体感。但**不要超过 ~2**，
  否则会出现不真实的"尖峰"感。
- 输出结构：`0.62 + 0.45*hs` —— 保留较大的环境光比例，避免背光面死黑压掉等高线。
  （一开始用 0.45+0.55，出图偏暗、阴影对比过强；调到 0.62+0.45 才接近纸质地形图的观感。）

## 4. 等高线：直接栅格化，不需要 matplotlib / GDAL / skimage

**踩过的坑**：`matplotlib.pyplot.contour` 出矢量折线看似优雅，但它是**重量级依赖**（本机 pip 装了几分钟没完），
而且为了 10⁷ 像素还要做一遍路径缩放。完全没必要。

**正解**——利用"等高线就是高程带边界"这一等价性，纯 numpy 向量化，毫秒级出图：

```python
b_minor = np.floor(dem_out / 20.0).astype(np.int32)      # 每 20 m 一条
m_minor = np.zeros_like(b_minor, bool)
m_minor[1:, :] |= b_minor[1:, :] != b_minor[:-1, :]      # 纵向带边界
m_minor[:, 1:] |= b_minor[:, 1:] != b_minor[:, :-1]      # 横向带边界
```

- **计曲线**（每 100 m 加粗）= `_dilate()` 对 `floor(dem/100)` 的边界做一次十字膨胀，再画在上层覆盖。
- 在**输出分辨率**上算（先把 DEM 用 `Image.fromarray(dem,'F').resize()` 双线性放大到输出尺寸），
  这样线宽天然是 1 px、边缘干净；不要在小栅格上算完再放大，会得到断断续续的锯齿。
- **间隔**：首曲线 20 m + 计曲线 100 m。九华山 13–1324 m 跨度，约 65 级，密度刚好。
  太密（10 m）在陡坡处糊成一片；「线覆盖 6.9% 像素」是个健康的量（见 §8 为何要压到这个数）。
- 线色不要用纯黑：首曲线 `(176,152,128)` 浅棕、计曲线 `(126,100,72)` 深棕，压在赭石色带上方最自然。

### 4.1 等高线高程标注——只有栅格线是不够的

**症状**：底图从"带高程数字的瓦片"换成"自渲染栅格线"之后，用户第一句反馈就是**"等高线标注没了"**。
纯线框地形图只能看出疏密，读不出绝对高度，实用性大打折扣。**数字是地形图的一半信息量。**

难点：栅格线只有"哪些像素是线"，**没有顺序也没有走向**。要沿线上写字，必须重新拿到矢量折线。
所以这里再走一遍 marching squares —— 但只对**活跃格**做 Python 循环，13 个 level 秒级完成：

```python
z = dem - level
code = (v0>=0) | ((v1>=0)<<1) | ((v2>=0)<<2) | ((v3>=0)<<3)   # 4 角点 16 种组合
rows, cols = np.nonzero((code > 0) & (code < 15))            # 只要活跃格
```
再按 16 种 case 查表连线段（**5/10 是鞍点歧义，拆成两段不相连**，别强行连），
最后按端点哈希拼成长折线，Douglas-Peucker 轻简（0.8 px）去掉冗余点。

摆放规则（都是实打实的踩坑结论）：

| 参数 | 值 | 为什么 |
|---|---|---|
| 只标计曲线 | 每 100 m | 20 m 首曲线全标 = "数字墙" |
| 相邻标注弧长间隔 | 560 逻辑 px | 太密数字比线还显眼 |
| 任意两标注最小间距 | 130 逻辑 px | 防不同 level 的数字在山脊上聚成一堆 |
| 局部倾角上限 | 62° | 更斜的字读不出来，**不如不标**（不是所有线都要有数字） |
| 走向估计窗口 | ±26 逻辑 px | 太短会被栅格锯齿带偏，太长会跨过弯道 |

三个必备细节：

1. **沿弧长采样，不是沿顶点采样**。折线顶点疏密极不均（RDP 后在直段上很稀），
   按顶点数间隔会导致一段挤满、一段空着。先 `cum = cumsum(hypot(diff))`，再按弧长取点。
2. **字要压掉底下的线**（纸质地形图的"断线注记"）：`stroke_width=2×SS`、`stroke_fill` 取纸色 `(252,250,245)`。
   这比"画一个白底方块再写字"干净得多，也不会出现灰色小方块。
3. **旋转写字要另开小图**：PIL 无法直接画旋转文字。做法是渲到一张透明小图 → `Image.rotate(-ang)` → `alpha_composite`。
   角度取局部走向且**先把切向量翻到 dx>0**（`if dx < 0: dx,dy = -dx,-dy`），
   这样角度必落在 (-90°, 90°]，**字永远不会头朝下**。

还要给标注**主动避让**：实测轨迹（攻略里还会再压一条粗实线）和 POI 图标都算禁标区，
否则数字会被粗线从中间切断。做法是建一个 `cell=14×SS` 的占用栅格——**和 `draw_osm.Labeller` 用同一个 cell 尺寸**，
于是等高线标注产出的占用集合能直接 `lab.grid |= seed` 塞给 OSM 注记层，让峰名/地名也绕开数字。两层注记互不打架。

**自检（必做）**：每个数字放好后用 DEM 反查该点高程，与 level 比对：

```python
errs.append(abs(float(dem[int(y/sy), int(x/sx)]) - lv))
```
正常应是「中位 1 m 级、最大 <10 m」。若普遍几十米，说明 MS 用的抽稀步长（`MS_STEP`）与栅格投影
没对齐，或 `scale` 传错——**这时宁可先不标，也别标错**。

## 5. 分层设色（hypsometric tint）

经典色带（低→高）：`草绿 → 黄绿 → 淡黄 → 土黄 → 赭石 → 棕 → 灰棕`。
用 `np.interp` 对三个通道分别线性插值即可，无需色卡文件。

合成：`最终RGB = 设色RGB × (0.62 + 0.45 × 晕渲)`。
**顺序不能反**——先设色后晕渲，晕渲只做明暗调制；先晕渲后设色会把地形细节洗掉。

## 6. 叠 OSM 矢量：地名、路网、水系、林地

地形底图**没有地名**，观感上会"空"。这就是"OSM 数据"那一半。

**为什么不用 OSM 官方瓦片**：`tile.openstreetmap.org` 的 Tile Usage Policy **明文禁止批量下载/爬取**，
一份攻略底图要上千张瓦片，属于批量。改用 **Overpass API 取 OSM 原始数据**（ODbL 许可，导出是正当用法），
自己渲染反而能完全控制配色、线宽、注记密度。

### 抓取（`fetch_osm.py`）

```python
[out:json][timeout:180];
(
  way["highway"~"^(motorway|trunk|...|steps|bridleway)$"]({{bbox}});
  way["waterway"~"^(river|stream|canal|drain)$"]({{bbox}});
  way["natural"="water"]({{bbox}});      way["landuse"="reservoir"]({{bbox}});
  way["natural"="wood"]({{bbox}});       way["landuse"="forest|meadow"]({{bbox}});
  node["place"~"^(city|town|village|hamlet|suburb|neighbourhood)$"]({{bbox}});
  node["natural"="peak"]({{bbox}});
  node["tourism"~"^(attraction|viewpoint|alpine_hut)$"]({{bbox}});
  node["amenity"="place_of_worship"]({{bbox}});
);
out geom;
```

- **`out geom`** 是关键：它把 way 的坐标**内联**在结果里，省掉第二次 `/api/0.6/ways?ways=...` 请求。
- 本 bbox（九华山 0.086°×0.186°）实测返回 **543 KB / 约 500 要素**，一次请求搞定，**不要**去碰 `china-latest.osm.pbf`。
- **必须配 3 个镜像轮询**（`overpass-api.de` → `kumi.systems` → `osm.jp`）+ 要素数下限校验
  （返回 <50 个要素就判为被限流，换镜像）。主站 429/504 是常态。
- 结果缓存 `out/osm.json`，加 `--force` 才重抓。**同一区域反复调样式时，永远只抓一次。**

### 绘制（`draw_osm.py`）——制图学优先，不是"把数据画上去"

| 要点 | 做法 |
|---|---|
| **面要素** | 画在**独立的 RGBA 图层**上再 `alpha_composite`，让下面的晕渲透出来。林地 α=95、草地 α=70、水体 α=225 |
| **道路** | 先画深色**描边**（宽 +2 px）再画浅色芯线 —— 这是纸质地形图的标准画法，道路立刻"浮"起来 |
| **步道** | 棕点线（`_dashed()` 自己按弧长切，PIL 没有虚线）。**故意与"攻略主线"的实线在视觉上区分开** |
| **山峰** | ▲ 三角 + `名 + ele` 双行小字 |
| **注记** | `Labeller` 类：14 px 网格占位，重叠就**跳过**。宁可少标不可糊成一片；按 city>town>suburb>village>hamlet 优先级排序后逐个尝试 |

- **投影必须复用同一套**：`make_projector(z, tx0, ty0, box, scale)`，
  公式 `out_px = (lonlat_to_px(lon,lat,z) - [tx0,ty0]*256 - box[0:2]) * scale`。
  和 DEM、和 SVG 层三处必须**完全一致**，否则线会整体错位。
- 中文字体：`C:/Windows/Fonts/msyh.ttc`（微软雅黑）。注记一律带 `stroke_width=2` 白描边，
  否则压在深色山体上读不出来。
- PIL 的 `ImageDraw.line(width=...)` **只接受 int**，传 float 会 `TypeError: 'float' object cannot be interpreted as an integer`。

### 顺序

面（林地→草地→水体）→ 线（水系→步道→公路）→ 注记。**注记最后画**，否则会被填充盖住。

## 7. 接进现有管线

`make_terrain.py` 的输出与 `build_base_map.py` **完全同构**，所以下游一行都不用改：

- `out/base_terrain.jpg` — 纯地形（晕渲 + 等高线 + 设色），保留下来便于调 OSM 样式时不用重算 DEM
- `out/base_map.jpg` — **最终底图**（地形 + OSM 叠加），`map_svg.py` 嵌的就是它
- `out/osm.json` — OSM 原始要素缓存
- `out/base_meta.json` — `{size, scale, raster, ss, box, bbox, z, tx0, ty0, source, attribution}`

于是 `map_svg.py` / `build_guide.py` 直接就能用新底图，轨迹、POI、剖面全部照旧。

## 8. 「放大看不清」——超采样是唯一实际有效的解法

这是本技能踩过的最大一次返工。**症状**：底图在正常尺寸下还行，一放大就是一团糊。
**根因**：底图栅格只有 1504 px 宽，而地图窗口塞了 8.3 km × 20.5 km。放大 = 无中生有。

### 解法：逻辑尺寸与栅格尺寸解耦

```python
LOGICAL_W = 1504          # 版式/SVG viewBox 用这个
SS        = 2             # 超采样倍数
RASTER_W  = LOGICAL_W * SS
```

- `base_map.jpg` 出 **RASTER_W**（3008）宽；
- `base_meta.json` 里 `size` 仍是 **[1504, 3775]**（逻辑），`scale` 按逻辑宽算；
- `map_svg.py` 的 `<image x="0" y="0" width="{IW}" height="{IH}">` 里 IW 是逻辑宽 1504 ——
  **浏览器会把 3008 的 jpeg 缩到 1504 个单位渲染**，这等于免费得到 2× 超采样：
  4 倍样本降采样 → 线与字明显更锐；放大到 200% 时还有真实像素。
- **下游一行都不用改**：SVG 的坐标、线宽、字号全部还在 1504 逻辑空间里。

### 三个配套细节（缺一个就白做）

1. **JPEG 必须 `subsampling=0`（4:4:4）**。PIL 在 quality<95 时默认 4:2:0，
   把色度通道砍到 1/4 分辨率 —— 地图全是彩色细线和小字，一砍就发虚挂彩边。
   实测体积代价很小（q86：6.54 MB vs 6.74 MB），**收益远大于代价**。
2. **放大用 BICUBIC，不要 LANCZOS**。LANCZOS 在陡崖等高反差处产生振铃，
   紧跟着的 USM 会把它放大成一片"颗粒噪点"（肉眼像水彩纸纹理）。
3. **USM 提锐要克制**：30 m DEM 在 z15 已过采样 7×，天生柔，必须提锐才有立体感；
   但 `(4, 85)` 这种重参数会把 DEM 过采样纹路一起提出来。**`(3, 55, 4)` 是个不错的起点**。

### 等高线要画细，不是画粗

`CONTOUR_DILATE = (0, 2)` @3008 px（首曲线不膨胀 = 发丝线，计曲线膨胀 2 次 ≈ 2.5 px 当量）。

20 m 间距在陡坡会密集成排，**线一粗就糊成"棕色泥"** —— 那才是"看不清"的主因，
比分辨率不足更致命。实测：把 (1,3) 改成 (0,2) 后线覆盖从 13.7% 降到 6.9%，
整张图立刻清爽。（颜色也一并调浅：首曲线 `(176,152,128)`、计曲线 `(126,100,72)`。）

### 还要单独出一张高清地图

攻略页里的地图受版式限制（左竖条）只有 ~1163 设备像素宽，**长图放大必然糊**。
要真正解决"放大看清"，必须额外给一张独立地图：
把同一份 `map_svg.build_svg()` 按 `RASTER_W`（3008）宽渲染、存 JPEG q92。
底图 1:1、矢量层 2× 超采样，放大到 100% 仍然锐利。见 `scripts/render_map_hi.py`。

## 9. 自检

- 底图高程范围应≈该区域真实范围（九华山本例 253–1345 m 量级）。若出现负值或 8000+，是解码公式错了。
- **投影对齐**：把轨迹画上去，线必须**贴着山脊/沟谷走**（晕渲能直接看出来）。错位就是 §2 的 z 不一致。
- **晕渲方向**：山体亮面应在**左上**。若在右下，说明 `dzdy` 符号或光源方位角反了。
- 等高线密度：陡坡处应明显变密、缓坡变疏。若均匀分布，说明 level 没取对或 DEM 是空数据。
- 瓦片缺失：脚本会打印 `WARN 缺失 n/m 块`，并已用中位数补洞；缺失多的话重跑（有缓存，只补缺的）。
- **清晰度自检（必做，别只看缩略图）**：
  1. 裁底图**原生 1:1** 的一小块看 —— 等高线应是干净细线、注记边缘锐利、无颗粒噪点；
  2. 再把底图缩到**攻略里实际显示的宽度**（约 1163 px）裁同一块，两者都该清爽；
  3. 出现"水彩颗粒"→ USM 太重或用了 LANCZOS；出现彩边虚边 → JPEG 没关 4:2:0；
     出现"棕色泥" → 等高线太粗或太深。

## 10. ⚠ 沙箱无外网时：用「文本 JSON 高程接口 + WebFetch」重建 DEM（贡嘎大环线实战）

**症状**：`make_terrain.py` 拿不到瓦片 —— `urllib`/`curl` 对 `s3.amazonaws.com`、Overpass、Nominatim
**全部超时**，即使 `dangerouslyDisableSandbox` 也一样（`HTTP_PROXY=127.0.0.1:12254` 不可达）。
但 **WebFetch / WebSearch 这两个工具本身能出网**（服务端代理）。

**做法**（唯一可行路径，贡嘎大环线已验证）：

1. 选一个**返回文本 JSON** 的高程服务 —— 瓦片 PNG 不行（WebFetch 会把二进制转成 markdown）。
   实测可用：`https://api.openelevation.org/v1/lookup?locations=lat,lon|lat,lon|...`
   （SRTM 30 m，免钥匙，**GET 单次上限约 300 个点**，URL 约 5 KB）。
   备选：`https://api.opentopodata.org/v1/srtm30m?locations=...`（单次 100 点）。
2. 按 bbox 生成规则网格（本例 44×59 km 用 **36×48 = 1728 点**，间距约 1.0×1.25 km），
   切成 300 点/片，逐个 WebFetch，**prompt 写死"只输出 elevation 数字，按原顺序逗号分隔，不要任何其它文字"**
   —— 让模型只回数字，输出体积能压到 1/5。
3. ⚠ **模型偶尔会多吐一个数**：收到后必须校验 `len(vals) == NLON*NLAT`，
   多/少了就从"最长的等值连续段"里删一个（这些位置都是 0 空值，后面本来就要插值补洞，删一个无影响）。
4. 本地插值成 DEM：
   - **SRTM 空值（返回 0）成片出现**在高山冰川区（贡嘎主峰一带 183/1728 个）。
     用"邻域有效值迭代填充"补洞，再对已知峰顶（贡嘎主峰 7556 m @101.8805,29.5953）
     做一次**锥面造型**把被抹平的主峰抬回来。纯圆锥会画出同心圆"靶心"，
     加一点方位角扰动（`1 + 0.13sin2θ + 0.09sin3θ + 0.06sin5θ`）就自然得多。
   - **重采样必须上三次插值**：`x` 方向经度等距，直接 PIL `BICUBIC`；
     `y` 方向 Mercator 非均匀，按真实 Mercator 纬度取分数行号再做 **Catmull-Rom**。
     用双线性会在 83 px 尺度留下**方格拼接感**，整张图变成"马赛克 + 云斑"。
5. **晕渲的 `res` 必须是栅格真实的米/像素**，不是 z15 瓦片分辨率：
   自渲染栅格的 m/px = `156543.03·cos(lat)/2^Z / (逻辑缩放比 × SS)`（本例 13.34，而非 4.13）。
   用错会让坡度估计差 3 倍。粗 DEM 先天平滑，垂直夸张给到 **2.8** 才有立体感。
6. **等高线间隔按插值精度定，不按真实 DEM 定**：控制点间距 1 km 时，
   20 m 首曲线会画成"指纹"，用 **首 100 m / 计 500 m**（线覆盖 4.7% 正好）。
7. **等高线高程标注要报偏差**：本例 51 个标注、DEM 反查偏差中位 2.7 m / 最大 14.4 m ——
   超过 10 m 说明控制网格与栅格投影没对齐，宁可先不标。
8. 诚实标注：底图与来源面板里写清"**地形为离线插值示意，等高线仅供大势参考，不用于导航**"，
   并说明 SRTM 空值与主峰补正。**不要假装是 30 m 分辨率 DEM。**

**同源三处的替代**：本路径没有 `draw_osm.py` 那一层（拿不到 OSM 矢量），
所以图例的"地形底图"组只保留 **计曲线 / 首曲线 / 雪线以上 / 地形晕渲** 四项，
**不要**再列"OSM 步道 / 公路 / 河流" —— 图例里出现图上没有的东西比不放图例更糟。

**顺带**：同一手法可用于查地名坐标 —— 但 Overpass 走 WebFetch 实测不稳
（`overpass-api.de` 返 406、`kumi.systems` 30 s 超时、Nominatim `fetch failed`），
地名还是靠 WebSearch 的公开攻略口径 + 轨迹作者自己的 KML 注记更可靠。
